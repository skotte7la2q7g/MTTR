SQL Application Resilience & MTTR Framework

Recovery baseline for the current estate. Anything not yet known is shown as NULL.

How this framework works

Three questions, answered from one inventory: what does each application depend on, how long does it take to bring each thing back, and what else comes down with it. Everything is derived from the workbook and, where collection was run, from read-only queries against the instances themselves. Recovery is counted one database at a time and one instance at a time, because that is the longest it can take. Read this panel first, then the Application Overview, then the SQL Instance MTTR panel.

The three failure scenarios

1 · A database is lost

Restore that database. Nothing is rebuilt.

MTTR = restore time for that one database
2 · An application is lost

Only the databases that application uses are restored. Other applications on the same instance are not in scope.

MTTR = SQL rebuild + restore of that application's databases + validation
3 · A SQL instance is lost

SQL Server is rebuilt and every database on it is restored, across all applications. No single application owns this number. If the VM has gone too, the VM build comes first.

MTTR = SQL rebuild + restore of all hosted databases + validation

Data replication and recovery mechanisms

Restore time is the baseline, not the plan. Where a replication mechanism exists, recovery is a failover and the restore figure becomes the fallback. Where one does not, the restore figure is the plan.

MechanismWhat recovery looks likeEffect on MTTRWhat still has to be captured
Always On availability group — synchronousAutomatic or manual failover to a replica that is already currentMinutes. The restore figure applies only if every replica is lostReplica count, listener, quorum design, tested failover date
Always On availability group — asynchronousManual failover, accepting the data behind the send queueMinutes, plus a data-loss decisionMeasured send-queue lag, who is authorised to accept the loss
Failover cluster instanceThe instance restarts on another node against the same storageMinutes, but storage loss is not covered — that falls back to restoreNode count, shared storage dependency, patching model
Log shippingManual role change, restore the outstanding log chainCopy and restore delay, plus the outstanding chainCopy/restore interval, monitored threshold, cutover runbook
Transactional / merge replicationNot a recovery mechanism. It moves data, it does not protect the databaseNo reduction. Restore applies, and replication must then be rebuiltTopology, re-initialisation cost after a restore
Backup and restore onlyRebuild, restore, roll forward, reconnectThe full figure in this reportBackup location and its own restore path, media integrity

How each restore time on this page was arrived at

Every database resolves down this ladder and stops at the first rung it can stand on. The rung is shown next to the figure, everywhere the figure appears — including as the coloured edge of every database on the relationship map.

RungBasisWhere it comes from
MeasuredA restore of this database that was actually timedA restore log on the instance (for example CommandLog), or a duration recorded in the workbook
DerivedThis database's own measured backup throughputmsdb.dbo.backupset: average size divided by average duration for this database on this storage, multiplied by the restore factor you set
NULLNothing measuredNo timed restore and no backup history. Reported as NULL and left out of every total, never filled in with an assumption
Why there is no assumed rung. An earlier version filled the gaps with an assumed restore throughput and a flat per-database figure. That produces a number precise enough to be quoted and soft enough to be wrong by an order of magnitude. Once collection has run, those gaps are real measurements instead — so until then they stay NULL, which is a fact somebody can act on.

Assumptions

Set these once. They are stored in this browser and every panel recalculates immediately — no need to re-run the PowerShell. Anything left blank stays NULL rather than defaulting to a number nobody chose.

Scope

What this covers

Which applications depend on which databases, on which instances, in which environments. The recovery arithmetic for the three failure scenarios above, and a step-by-step run-down of the four scenarios you can pick. Measured size, compatibility level, backup history, restore history and replication design wherever collection was run.

What it does not cover

None of these are oversights. It does not verify that a backup is restorable — only a restore proves that. It does not model a site-wide failure, because shared teams and bandwidth break the arithmetic. It does not cover application-tier recovery, network, storage or middleware. It does not price anything. The scenario run-downs name detection, decision-making, failover and log restores, but do not time them — nothing on this estate measures them.

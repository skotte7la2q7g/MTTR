Chapter 01 · SQL Server releases

SQL Server versions, 2008 to 2025

Each SQL Server release has a product version (10.x, 11.x … 17.x) and a matching database compatibility level (100, 110 … 170). The engine version decides what the server can do. The compatibility level decides how the optimizer and T-SQL behave for one database. You can run a database at level 130 on a 2022 engine, which is why upgrades can be done in two safe steps: move the engine first, raise the compatibility level later.

Editions and licensing in one view

  • Since 2012, Enterprise is licensed per core (minimum 4 cores per physical processor or per VM). Standard is per core or Server + CAL.
  • 2016 SP1 gave Standard, Web and Express the same programmability surface as Enterprise. The difference is now scale limits and enterprise-only HA/performance features (full AGs, online index operations, more memory, partition-aware parallelism, Resource Governor until 2025).
  • Software Assurance gives free passive replicas: one for HA, one for DR, and one in Azure. A passive replica must not serve reads or backups beyond what the licence terms allow, so read-scale secondaries need a licence.
  • Azure Hybrid Benefit lets you reuse SA licences for Azure SQL and SQL on Azure VMs. Pay-as-you-go through Azure Arc (2022+) bills on-prem cores monthly.
  • 2025 edition changes: Standard raised to 4 sockets or 32 cores and 256 GB of buffer pool memory; Express database limit raised to 50 GB; new free Standard Developer edition next to Enterprise Developer; Web edition discontinued.

Removed or retired: flag these in any architecture review

  • deprecated Database mirroring (since 2012). Use AGs.
  • removed 2022 SQL Server Native Client (SNAC). Use MSOLEDBSQL or ODBC Driver 18. Note that ODBC 18 / OLE DB 19 default to Encrypt=Yes, which breaks connections to servers with self-signed certificates unless you fix the certificate or set TrustServerCertificate.
  • removed 2022 Big Data Clusters, PolyBase Hadoop connectivity and scale-out groups. R/Python runtimes no longer installed by setup.
  • deprecated 2022 Stretch Database.
  • removed 2025 Master Data Services and Data Quality Services, Synapse Link for SQL (replaced by Fabric mirroring), Purview access policies. Important for this role because the JD asks for MDM practice.
  • reporting SSRS 2022 is the last SSRS release; Power BI Report Server is the on-prem reporting server from 2025.
  • tools Azure Data Studio retired 28 Feb 2026. Use SSMS 21/22 (64-bit, Git, Copilot) or VS Code with the mssql extension.

For an architect role, interviewers rarely want a list of features. They want to know whether you can turn version knowledge into a roadmap: which estates to upgrade, to what target, in what order, how you control plan regressions, and what licensing or support risk you remove.

Real-time scenarios

The company has 40 instances on 2012, 2014 and 2016. 2016 just went out of extended support. The CIO asks you for an upgrade roadmap. What do you present?
  1. Inventory and classify. Collect version, edition, size, cores, HA setup, features in use (sys.dm_db_persisted_sku_features), linked servers, SSIS/SSRS dependencies, CLR, cross-database queries, vendor certification. Tag each database by criticality and RPO/RTO.
  2. Pick a target per workload. Vendor apps that only certify old versions: SQL 2022 at the vendor's compat level. Home-grown OLTP: SQL 2022/2025 or Azure SQL MI. Analytics: consider Fabric or Synapse instead of a like-for-like move. Low-value databases: consolidate.
  3. Risk first. Out-of-support 2012/2014/2016 servers go first. If they cannot move in time, buy Extended Security Updates (free when the workload runs in Azure) as a bridge, not a plan.
  4. Method. Prefer side-by-side (new server, restore, AG or log shipping for cutover) over in-place, so rollback is "point the DNS back".
  5. Plan stability. Keep the old compat level on day 1, turn on Query Store, capture a baseline, then raise the compat level per database and fix regressions with plan forcing or Query Store hints.
  6. Waves. Pilot with low-risk databases, then waves grouped by application dependency. Each wave has a rehearsal, a cutover runbook and a rollback point.
  7. Benefits to state. Security patches, Query Store and IQP, ADR, better HA, licence consolidation (fewer, bigger hosts), Entra ID and Defender coverage.
After moving a database from SQL 2014 to SQL 2022 and switching to compat 160, the month-end sales report goes from 40 seconds to 9 minutes. What do you do?
  • Stop the bleeding. If you captured a baseline in Query Store at the old level, force the old plan for that query (sp_query_store_force_plan). If not, add a Query Store hint such as USE HINT('QUERY_OPTIMIZER_COMPATIBILITY_LEVEL_120') or FORCE_LEGACY_CARDINALITY_ESTIMATION for that one query, without touching the application.
  • Find the cause. Compare old and new plans: estimates vs actuals, join types, memory grants, parallelism. The usual causes are CE model differences (correlation or containment assumptions), a different join order, or a memory grant spill.
  • Fix properly. Update stats with a better sample, add a missing index, rewrite a non-sargable predicate, or keep the hint permanently and document it.
  • Process lesson. Upgrade compat levels only with Query Store running and a baseline captured. Automatic plan correction (FORCE_LAST_GOOD_PLAN) can catch many of these by itself.
A vendor ERP is certified only at compatibility level 130, but infrastructure wants everything on SQL Server 2022. Is that a problem?

No. SQL Server 2022 supports compat levels 100 to 160. Run the vendor database at 130 on the 2022 engine. You still get engine-level gains (ADR, Query Store on by default, tempdb latch improvements, contained AGs, Ledger, backup improvements, security patches). You do not get optimizer features gated to 140/150/160 such as adaptive joins, scalar UDF inlining or PSP. Document it as a supported configuration and agree with the vendor on the path to a newer level.

The business wants to build its product master in Master Data Services on the new SQL Server 2025 estate. How do you respond?

MDS (and DQS) are removed in SQL Server 2025, so a new MDS build would be dead on arrival. Options: keep an existing MDS on SQL 2022 until its support ends (Jan 2033) as a tactical choice, or pick a supported MDM product (Profisee is Azure-native and integrates with Purview; Informatica, Reltio, Semarchy and Stibo are common in CPG and retail). For a small reference-data need, a governed set of tables with stewardship screens (Power Apps) and approval workflow can be enough. Design the golden record, match rules and survivorship first; the tool choice comes after.

Interview questions

What is the difference between the SQL Server product version and the database compatibility level?

The product version is the engine binary (for example 16.0 for 2022). The compatibility level is a per-database setting that controls T-SQL behavior and which optimizer behaviors and fixes apply (for example 160). A newer engine supports older levels, so you can upgrade binaries without changing plan behavior, then raise the level later under control. New syntax (for example GENERATE_SERIES) and IQP features are often gated by the level.

Walk me through the headline feature of each release from 2008 to 2025.

2008: TDE, compression, MERGE, CDC. 2008 R2: MDS, PowerPivot. 2012: Availability Groups, columnstore, window functions. 2014: In-Memory OLTP, new CE, updatable CCI. 2016: Query Store, temporal, Always Encrypted, RLS, and SP1 feature parity for Standard. 2017: Linux, adaptive QP, automatic tuning. 2019: Intelligent QP, ADR, UTF-8. 2022: Azure link to MI, Ledger, PSP, contained AGs, S3/Parquet virtualization. 2025: vector search and AI functions, JSON type, regex, optimized locking, Fabric mirroring.

Why was 2016 SP1 such an important release for architects?

It moved programmability features into all editions: partitioning, columnstore, data compression, In-Memory OLTP, database snapshots, Always Encrypted, RLS, DDM, PolyBase and fine-grained auditing. From then on, the code that runs on Enterprise runs on Standard. You choose the edition by scale (cores, memory) and enterprise operational features (full AGs, online index rebuilds, partition parallelism, TDE before 2019), not by T-SQL surface. It made Standard viable for many mid-size warehouses.

What changed with the cardinality estimator in 2014, and how do you deal with regressions it causes?

CE 120 changed core assumptions. The old model assumed column predicates are independent; the new one assumes some correlation (exponential backoff). It also changed join containment from simple to base containment and improved estimates for ascending keys beyond the histogram. Most queries got better, some got much worse. Handle regressions per query: Query Store plan forcing, USE HINT('FORCE_LEGACY_CARDINALITY_ESTIMATION') as a query or Query Store hint, or LEGACY_CARDINALITY_ESTIMATION = ON as a database-scoped setting if the whole application suffers. Since 2022, CE feedback can fix some model mismatches automatically.

How do you plan an upgrade so that query plans don't regress?
  1. Upgrade the engine and keep the old compat level.
  2. Turn on Query Store and run a full business cycle (including month-end) to capture baseline plans.
  3. Raise the compat level, in test first. Database Experimentation Assistant or replayed workloads help here.
  4. Use Query Store's regressed queries report, force good plans or add hints, and let automatic tuning (FORCE_LAST_GOOD_PLAN) catch the rest.
  5. Keep the old level as a quick rollback for the whole database.

Microsoft calls this the Query Tuning Assistant workflow in SSMS.

In-place upgrade or side-by-side migration: which do you recommend and why?

Side-by-side for anything important. You build a clean server on a supported OS, restore and sync the databases (log shipping, AG, or backup/restore), test properly, and cut over by changing a DNS alias or listener. Rollback is simple because the old server is untouched. In-place is faster and keeps the server name, but rollback means a rebuild and restore, and you carry old OS and configuration baggage. In-place is fine for dev/test or small, low-risk servers.

What does "CU-only servicing" mean and how do you patch now?

From SQL Server 2017 there are no service packs. Microsoft ships Cumulative Updates (roughly every 1-2 months early in life, then less often) and GDRs (security-only). Choose one track per server: the CU track gets fixes and features; the GDR track only gets security fixes, and you can move from GDR to CU but not back. Practice: test each CU in lower environments, patch AG secondaries first, fail over, then patch the old primary. Keep within the last one or two CUs.

SQL Server 2016 left extended support in July 2026. What options does the business have?
  • Upgrade in place or side by side to 2022 or 2025.
  • Move to Azure SQL Managed Instance or Azure SQL Database (no more version upgrades).
  • Lift to an Azure VM, where Extended Security Updates are free, buying time for a proper upgrade.
  • Buy ESU on-prem (paid yearly, up to three years, usually through Azure Arc).

ESU only gives critical security fixes. It is a bridge, not a strategy.

What features are available on SQL Server on Linux, and what's missing?

The database engine is the same code (through the SQL Platform Abstraction Layer), including AGs (with Pacemaker, cluster type EXTERNAL or NONE), FCIs with Pacemaker, Agent, full-text, PolyBase, ML Services and replication (2019+). Missing or different: SSAS, SSRS and Power BI Report Server (Windows only), no WSFC, no FILESTREAM, no Windows authentication without AD integration setup (it is supported through Kerberos/keytab), and some third-party tools. Containers (Docker, Kubernetes) are a common use for dev/test and CI.

How has columnstore evolved, and what does that mean for warehouse design on SQL Server?

2012 had a read-only nonclustered columnstore, so you had to drop and rebuild it on each load. 2014 brought updatable clustered columnstore, which made it the default for fact tables. 2016 added updatable NCCI on rowstore tables (OLTP plus analytics on the same table), better batch mode and string predicate pushdown. 2019 brought batch mode to rowstore tables. 2022 added ordered CCI for better segment elimination, and 2025 added ordered NCCI and online ordered builds. So on modern versions large fact tables should be CCI, partitioned by date, loaded in batches of at least 102,400 rows to go straight to compressed rowgroups.

Trace the evolution of high availability features from mirroring to SQL Server 2025.

Mirroring (2005) protected one database to one partner. AGs (2012) grouped databases with up to 4 secondaries and readable replicas; 2014 raised that to 8. 2016 brought Basic AGs on Standard, distributed AGs (AG of AGs, across clusters or regions) and DTC support. 2017 added clusterless and Linux AGs. 2019 allowed 5 synchronous replicas and connection redirection. 2022 introduced contained AGs (logins and jobs travel with the AG) and the link to Azure SQL MI. 2025 allows full and differential backups on secondaries and improves failover speed and health detection.

What are the main T-SQL language additions you'd actually use from each version?
  • 2008: MERGE, TVPs, GROUPING SETS, compound assignment (+=)
  • 2012: OFFSET/FETCH, LAG/LEAD, window frames (ROWS BETWEEN), THROW, TRY_CONVERT, IIF, CONCAT, FORMAT, EOMONTH, SEQUENCE
  • 2016: DROP IF EXISTS, STRING_SPLIT, JSON functions, AT TIME ZONE, temporal FOR SYSTEM_TIME, CREATE OR ALTER (SP1)
  • 2017: STRING_AGG, TRIM, CONCAT_WS, TRANSLATE
  • 2019: APPROX_COUNT_DISTINCT, UTF-8 collations
  • 2022: GENERATE_SERIES, DATE_BUCKET, DATETRUNC, GREATEST/LEAST, IS [NOT] DISTINCT FROM, WINDOW clause, STRING_SPLIT ordinal, APPROX_PERCENTILE, JSON_OBJECT/JSON_ARRAY, bit functions
  • 2025: regex functions, || concatenation, CURRENT_DATE, PRODUCT, UNISTR, BASE64_ENCODE/DECODE, fuzzy matching, vector and AI functions, json type
How do you find which Enterprise-only features a database uses before moving it to Standard?

Query sys.dm_db_persisted_sku_features in each database. It lists features that would stop the database from being restored or attached on a lower edition. Since 2016 SP1 the list is short (for example TDE before 2019 on Standard). Also check instance-level needs: full AGs vs Basic AG, online index operations, memory and core limits, Resource Governor (Standard from 2025), and partitioned table parallelism.

Explain the Software Assurance passive replica benefit. Why does it matter in HA/DR design?

With SA (or subscription licences), you can run one passive secondary for HA, one passive secondary for DR, and one passive replica in Azure without licensing those cores. "Passive" means no read workload and no production use beyond limited tasks such as DBCC, log backups and monitoring. Once you send reports or full backups to a secondary it becomes active and needs a licence. This often decides whether a design offloads reads to a secondary or keeps it passive.

What breaks when you upgrade client drivers to ODBC 18 or OLE DB 19?

Both default to Encrypt=Yes (mandatory). Clients that connect to servers with a self-signed or untrusted certificate fail with certificate trust errors. Fix it properly by installing a CA-signed certificate on SQL Server that matches the server name, or as a short-term workaround set TrustServerCertificate=Yes. SQL 2022 also supports TDS 8.0 with Encrypt=Strict, where TLS is negotiated before any TDS traffic. SNAC was removed in 2022, so legacy apps must move to MSOLEDBSQL.

How did tempdb change across versions, and what is your current tempdb standard?

2016 setup creates multiple data files and applies the old TF 1117/1118 behavior (uniform extents, all files grow together) by default. 2019 added memory-optimized tempdb metadata to remove system table latch contention. 2022 removed most GAM/SGAM page latch contention. 2025 added tempdb space limits per workload group and ADR in tempdb. Standard: equal-size files, 8 files to start (or one per core up to 8), add in groups of 4 only if PAGELATCH waits remain, fast dedicated storage, pre-sized to avoid autogrowth, and memory-optimized metadata on for heavy temp table workloads.

Can you restore a SQL Server 2012 backup on SQL Server 2022 or 2025? What happens to it?

Yes, a backup from 2012 can be restored on 2022 (2008 and later are supported as sources). During restore the database is upgraded in place to the new internal version, and that cannot be reversed: you cannot restore it back to the old version. Its compat level stays as it was unless it is below the minimum supported (100), in which case it is raised to the minimum. In-place setup upgrades have stricter source-version rules than restore, so check the supported upgrade matrix for the specific target.

What is the difference between SQL Server 2008 and 2008 R2?

Same engine family and compat level (100). R2 added Master Data Services, PowerPivot for Excel/SharePoint, StreamInsight (complex event processing), Unicode compression, the Utility Control Point for multi-server management, backup compression in Standard, and the Datacenter and Parallel Data Warehouse editions.

Why might you deliberately keep a database at compat 150 after moving to SQL 2022?

Vendor certification; a known regression at 160 that you have not fixed yet; or a deadline where you want the engine benefits now and plan-behavior change later. You still get the engine improvements. You lose PSP optimization, DOP feedback, CE feedback and the 2022 T-SQL syntax gated to 160. Keep a dated plan to move up, because staying on old levels for years builds technical debt.

Name the features Microsoft removed or retired that you would flag in a design review today.

Database mirroring (deprecated), SNAC (removed 2022), Stretch Database (deprecated), Big Data Clusters and PolyBase Hadoop (removed 2022), MDS and DQS (removed 2025), Synapse Link for SQL (replaced by Fabric mirroring), SSRS (Power BI Report Server from 2025), Azure Data Studio (retired Feb 2026), Azure Synapse dedicated pools (no new features; Fabric is the forward path). Also old Windows Server versions and TLS 1.0/1.1.

What are Extended Security Updates and when would you recommend them?

ESU is a paid program that delivers critical security updates for up to three years after extended support ends. It covers security fixes only, with no new features or non-security fixes. It is free for workloads moved to Azure VMs or Azure Stack, and on-prem it is bought yearly (usually billed through Azure Arc). Recommend it only as a bridge when an upgrade cannot finish before end of support, with a dated exit plan.

Chapter 02 · SQL Server 2022 (16.x, compat 160)

SQL Server 2022 in depth

SQL Server 2022 has three themes. Azure-connected: a live link to Azure SQL Managed Instance for DR, Entra ID logins, Purview governance and Defender. Smarter optimizer: it can keep several plans for one query (PSP), learn better parallelism and estimates from history (DOP and CE feedback), and lets you add hints without touching code (Query Store hints). Trust and open data: tamper-evident Ledger tables, and direct T-SQL over Parquet, CSV and Delta files in S3 or Azure storage.

Azure-connected features

  • Link feature for Azure SQL Managed Instance: a distributed-AG-based link that replicates a database to MI in near real time. Use cases: DR in Azure, read offload to MI, and online migration. With SQL 2022 you can fail over to MI and fail back.
  • Microsoft Entra ID authentication (Azure AD) for on-prem SQL through Azure Arc, including MFA and groups.
  • Microsoft Purview integration: scan and classify, lineage. Purview access policies are removed in 2025.
  • Azure Synapse Link for SQL: near real-time replication of operational tables into Synapse dedicated pools. Superseded by Fabric mirroring, and removed in 2025.
  • Microsoft Defender for SQL and pay-as-you-go billing through Azure Arc.

Ledger

Ledger makes data tamper-evident. Each transaction is hashed into a blockchain-style chain; periodic database digests (the latest hash) are stored somewhere the DBA can't change, such as immutable Azure Blob storage or Azure Confidential Ledger. Anyone can later verify that history was not changed, even by a sysadmin. It is tamper-evident, not tamper-proof: it detects changes, it doesn't prevent them.

  • Updatable ledger table: normal DML, with a history table of prior row versions (like temporal tables).
  • Append-only ledger table: inserts only. Good for audit logs, scans or event records.
  • Ledger database: every table is a ledger table.
CREATE TABLE dbo.PriceChange
( PriceChangeId bigint IDENTITY PRIMARY KEY,
  Sku           varchar(20)  NOT NULL,
  OldPrice      decimal(9,2) NOT NULL,
  NewPrice      decimal(9,2) NOT NULL,

WITH (SYSTEM_VERSIONING = ON, LEDGER = ON);      -- updatable ledger

Availability and storage

  • Contained availability groups: the AG carries its own master and msdb, so logins, users, permissions and Agent jobs created through the AG listener fail over with it. This removes the old "sync logins and jobs by script" chore.
  • Distributed AG throughput improvements, and better handling for large log volumes.
  • T-SQL snapshot backup: ALTER DATABASE ... SET SUSPEND_FOR_SNAPSHOT_BACKUP = ON, take a storage snapshot, then BACKUP DATABASE ... WITH METADATA_ONLY. Near-instant backups of very large databases without VSS writers.
  • Backup to S3-compatible object storage (MinIO, Pure, NetApp, AWS S3) with BACKUP ... TO URL = 's3://...'.
  • Intel QAT backup compression (hardware offload) as an alternative algorithm.
  • Instant file initialization for log growth up to 64 MB and a simpler VLF formula, so small autogrowths no longer stall the log.
  • Shrink with WAIT_AT_LOW_PRIORITY so a shrink no longer blocks the workload on its schema lock.
  • Buffer pool parallel scan for large-memory servers, and GAM/SGAM concurrency in tempdb.
  • Multi-write replication: peer-to-peer with last-writer-wins conflict handling.

Data virtualization (PolyBase rebuilt)

The Hadoop-based PolyBase is gone. 2022 uses REST APIs to read and write object storage directly: Azure Blob/ADLS Gen2 and any S3-compatible storage, in Parquet, CSV and (read-only) Delta formats. Real-time scenarios

A stored procedure that searches orders by customer is fast for most customers and terrible for your three largest retail accounts. You're on SQL 2022. What happens and what do you do?

This is parameter sniffing: the plan compiled for a small customer (seek plus key lookups) gets reused for a customer with millions of rows. On 2022 at compat 160, PSP optimization may already help: if the predicate column has a skewed histogram, the optimizer builds a dispatcher plan with low/medium/high cardinality variants. Check sys.query_store_query_variant. If PSP doesn't kick in (it only applies to equality predicates on skewed columns, and has limits), the choices in order are:

  1. Query Store hint OPTION(RECOMPILE) if the procedure runs rarely enough that compile cost is fine.
  2. OPTIMIZE FOR a representative value, or OPTIMIZE FOR UNKNOWN.
  3. Branch the logic: route the top accounts to a separate procedure with its own plan.
  4. Fix the index so one plan is good for everyone (a covering index removes the lookups).
Leadership wants a DR copy of the on-prem order database in Azure with minimal work and the option to fail back. You're on SQL 2022 Enterprise.

Use the Managed Instance link. It uses distributed AG technology to replicate the database asynchronously to an Azure SQL MI. The MI copy is readable, so reporting can use it. In a disaster you fail over to MI (planned or forced); with SQL 2022 you can fail back by re-establishing the link in the other direction. Design points: network (ExpressRoute or VPN, port 5022), MI sizing for the write load, licensing (a passive DR replica may be covered by the hybrid failover rights), log throughput, and a runbook that repoints application connection strings. Interview questions

Explain Parameter Sensitive Plan optimization. How is it different from OPTION(RECOMPILE)?

PSP lets one parameterized query keep up to three cached plans. At compile time the optimizer finds a predicate on a column with a skewed histogram and defines cardinality boundaries. It caches a dispatcher plan that, at run time, checks the parameter value's estimated cardinality and routes to the matching query variant plan. RECOMPILE builds a new plan on every execution: always well-fitted but costs CPU on every call and leaves less history. PSP gives most of the benefit with plan reuse. It needs compat 160 and works for equality predicates; it doesn't fix every sniffing case.

What are Query Store hints and why are they better than plan guides?

Query Store hints attach OPTION(...) hints to a query by its Query Store query_id using sys.sp_query_store_set_hints. No code change, so they work for vendor apps and ORMs. They persist across restarts and plan cache flushes, are easy to see (sys.query_store_query_hints) and remove. Plan guides require matching the exact statement text and parameter definition, are hard to manage and break silently when the text changes. Query Store hints override plan guides and hard-coded hints when they conflict.

What does DOP feedback do and when would you turn it on?

For repeating queries, it watches CPU time, elapsed time and parallelism waits. If a query wastes CPU through excessive parallelism, it lowers DOP in steps (never below 2, and never above MAXDOP), validates each step, and keeps it only if the query doesn't get slower. Changes persist in Query Store. Turn it on for mixed OLTP/reporting servers with high CXPACKET/CXCONSUMER waits and CPU pressure, where a lower DOP frees CPU for concurrency.

What is CE feedback?

When a repeating query shows big estimate errors, the engine checks whether a different model assumption would have fitted better: correlated vs independent predicates, simple vs base join containment, or row-goal behavior. It tests the alternative on later executions and, if the plan improves, keeps it as a Query Store hint. If it doesn't improve, it reverts. It's automatic correction of known CE model weaknesses, at compat 160 with Query Store on.

What is the Managed Instance link and what are its use cases?

A replication link between SQL Server (2016 SP3+, best on 2022) and Azure SQL MI built on distributed AGs. Changes stream asynchronously to MI, where the database is readable. Uses: DR in Azure without a second datacenter, read-only reporting offload, and near-zero-downtime migration (cut over when ready). With SQL 2022 you can fail over to MI and fail back to SQL Server.

Explain Ledger. Is it the same as blockchain? Is it the same as temporal tables or audit?

Ledger hashes every transaction and chains the hashes, like a blockchain, but it's centralized: no consensus, no decentralization. The latest hash (digest) is stored outside the database in tamper-proof storage, and verification recomputes the chain to detect changes. Temporal tables keep history but anyone with permission can change both current and history rows. SQL Audit records who did what, but doesn't prove the data itself wasn't changed. Ledger gives cryptographic proof of integrity. Limits to know: you can't turn a ledger table back into a normal one; some data types and features aren't supported; and storage grows because history is kept.

What problem do contained availability groups solve?

In a classic AG only user databases fail over. Logins, SQL Agent jobs and server permissions live in each replica's own master and msdb, so you sync them with scripts or tools (dbatools), and forgotten jobs or logins cause outages after failover. A contained AG has its own master and msdb inside the AG. When you connect through the listener and create a login or job, it's stored in the AG and fails over with it. Things to watch: you must connect through the listener for administration, and instance-level objects outside the AG are still separate.

How does the T-SQL snapshot backup work and when is it useful?

ALTER DATABASE db SET SUSPEND_FOR_SNAPSHOT_BACKUP = ON freezes writes (I/O) for that database or a group of databases. You then take a storage-array or cloud disk snapshot, and run BACKUP DATABASE db TO DISK='...' WITH METADATA_ONLY, which writes a small metadata file and resumes I/O. It replaces VSS-based snapshot backups. For a 50 TB database it brings backup time from hours to seconds, and restore is a snapshot revert plus log backups. You still need regular log backups and must test the restore path.

What is CETAS and how does it help a data architect?

CREATE EXTERNAL TABLE AS SELECT writes the result of a query to files (Parquet or CSV) in Azure storage or S3 and creates an external table over them. Uses: archiving cold partitions to cheap storage while keeping them queryable; exporting data for a lakehouse or data science team; feeding Spark or Fabric without an extra ETL tool. Requires sp_configure 'allow polybase export', 1.

What T-SQL improvements in 2022 do you use most and why?

GENERATE_SERIES replaces number/tally tables. DATE_BUCKET and DATETRUNC simplify weekly or fiscal-period grouping. GREATEST/LEAST replace long CASE expressions. IS [NOT] DISTINCT FROM makes NULL-safe comparisons readable, which matters in SCD2 change detection. The WINDOW clause reduces repetition in window functions. STRING_SPLIT with ordinal finally guarantees element order. APPROX_PERCENTILE_CONT gives fast medians. Most need compat 160.

What are the new built-in server roles in 2022 and why do they matter?

Fixed server roles with ##MS_...## names, such as ServerStateReader, ServerStateManager, DefinitionReader, DatabaseConnector, DatabaseManager, LoginManager, SecurityDefinitionReader and PerformanceDefinitionReader. They let you grant monitoring, deployment or login-management rights without sysadmin. For example, a monitoring tool gets ##MS_ServerStateReader## plus ##MS_DefinitionReader##. This supports least privilege and separation of duties audits.

What is an ordered clustered columnstore index and when does it help?

A CCI built with ORDER (column) sorts data on that column before compressing it into segments. Each segment then covers a narrow min/max range, so range predicates on that column eliminate more segments. It helps when most queries filter on one column (usually a date or date key). It costs extra build time and memory (sort), and ordering degrades as new data arrives through the delta store, so rebuild partitions periodically.

How does memory grant feedback work, and what did 2022 add?

After a query runs, the engine compares the memory granted with what was actually used. If it spilled, the next execution gets more; if it used far less, the next gets less. Batch mode got it in 2017, row mode in 2019. Older versions adjusted on the last execution only, which caused oscillation for queries with varying parameters, and the feedback was lost when the plan left the cache. 2022 uses a percentile of recent executions and persists feedback in Query Store.

What's new in Always Encrypted for 2022?

With secure enclaves (VBS on SQL Server), 2022 allows JOIN, GROUP BY and ORDER BY on encrypted columns, plus UTF-8 collations, in addition to the 2019 support for range comparisons, LIKE and in-place encryption. That makes encrypting columns such as national IDs practical for more query patterns. Keys stay with the client, so DBAs can't see plaintext.

What is Synapse Link for SQL and what replaced it?

Synapse Link for SQL (2022) streamed changes from SQL Server or Azure SQL DB tables into an Azure Synapse dedicated pool in near real time, avoiding ETL for operational reporting. It is removed in SQL Server 2025. Fabric mirroring replaces it: it replicates tables into OneLake as Delta tables, queryable by the SQL endpoint, Spark and Power BI Direct Lake.

Name three 2022 improvements for very large databases.
  • T-SQL snapshot backups for near-instant backup and restore.
  • Buffer pool parallel scan, which speeds up operations that scan the whole buffer pool (database startup, DBCC, dropping large objects) on servers with lots of memory.
  • Resumable ADD CONSTRAINT and ordered CCI; shrink with WAIT_AT_LOW_PRIORITY; IFI for small log growths; Intel QAT compression for faster backups.
Query Store is on by default in 2022. What settings do you still review?

Max size (default 1 GB is small for busy OLTP; 2-10 GB is common), capture mode (AUTO, or CUSTOM to ignore trivial queries), stale query threshold (retention days), data flush interval, and size-based cleanup. Watch for READ_ONLY flips when it fills up, and for ad hoc workloads that flood it with single-use queries. Turn on Query Store for readable secondaries if you offload reporting there.

What is Intel QAT backup compression?

An alternative backup compression algorithm (COMPRESSION (ALGORITHM = QAT_DEFLATE)) that offloads compression to Intel QuickAssist hardware, or runs in software mode. It reduces CPU use during backups and can make them faster. You enable it with sp_configure 'hardware offload enabled' and ALTER SERVER CONFIGURATION SET HARDWARE_OFFLOAD. SQL 2025 adds ZSTD as another software option.

AI and vector search

An embedding is an array of numbers (for example 1,536 floats) produced by a model. Texts with similar meaning get vectors that are close together. Vector search finds the rows closest to a question's vector. This is the core of RAG (retrieval-augmented generation): find the relevant rows, then give them to an LLM to answer.

The sales team wants a "product assistant" that answers questions from product spec sheets, allergen data and promo rules stored in SQL Server. Design it on SQL Server 2025.
  1. Ingest and chunk: load spec sheets as text; use AI_GENERATE_CHUNKS (or chunk in the pipeline) into about 300-800 token chunks with some overlap; keep SKU, brand, market and document version as columns.

  3. Search: hybrid retrieval: filter by structured columns first (market = 'US', active = 1), then rank by VECTOR_DISTANCE, or use a DiskANN index with VECTOR_SEARCH when rows reach the millions. Optionally combine with full-text search for exact product codes.
  4. Generate: the app (or an Azure Function) sends the top chunks plus the question to an LLM and returns the answer with sources.
  5. Keep fresh: re-embed only changed rows (a hash of the text, or change tracking / CES events).
  6. Govern: RLS so users only retrieve chunks they're allowed to see, auditing of prompts, no PII in the embedded text, cost monitoring of model calls.

Why in SQL: data stays in one governed, backed-up, HA store with joins to master data, instead of syncing to a separate vector database.

An order entry system has heavy blocking and frequent lock escalation during the nightly price update that touches 5 million rows. You move to SQL 2025. What changes and what would you configure?

Turn on ADR, RCSI and optimized locking. With TID locking the update holds one TID lock instead of millions of row locks, so lock memory stays flat and lock escalation to a table lock (the thing blocking order entry) doesn't happen. With LAQ, order-entry updates check rows against the latest committed version before locking, so they wait only on rows that truly conflict. Still batch the price update (for example 50,000 rows per transaction) to keep log and version store growth small. Test RCSI first: code that relies on readers blocking (for example "read then update" without UPDLOCK) can behave differently.

The data team wants near real-time order events in Kafka for a demand-sensing model. Today they poll CDC tables every minute. What do you propose on SQL 2025?

Use change event streaming to push committed changes on the Orders and OrderLines tables to Azure Event Hubs, consumed through its Kafka endpoint. Events are CloudEvents in JSON or Avro, so consumers don't need SQL access or a polling job. Compare with alternatives: CDC + Debezium (mature, but more moving parts), Fabric mirroring (if the target is analytics in OneLake rather than an event stream). Plan for: schema change handling, event ordering per key, replay and retention in Event Hubs, monitoring lag, and the preview status of CES at GA.

A reporting procedure uses WHERE (@Region IS NULL OR Region = @Region) AND (@Brand IS NULL OR Brand = @Brand). It's slow for some calls. What's your fix on 2022 vs 2025?

The single cached plan must work for every combination of NULL and non-NULL, so it scans. On 2022 the usual fixes are OPTION(RECOMPILE) (the optimizer then embeds actual values and removes dead branches), or dynamic SQL built with only the needed predicates and still parameterized through sp_executesql. On 2025 at compat 170, OPPO can cache separate plan variants for the NULL and non-NULL cases automatically. For many optional filters, dynamic SQL is still the cleanest and most predictable choice.

A runaway ad hoc query from a BI tool fills tempdb every Monday and takes down the server. What 2025 features help?
  • Resource Governor GROUP_MAX_TEMPDB_DATA_MB on the BI workload group: the query that exceeds it fails, the server survives.
  • Query Store hint ABORT_QUERY_EXECUTION on that specific query_id until the report is fixed.
  • ADR in tempdb to speed rollback of large temp operations.
  • Then fix the cause: a missing join predicate, a huge sort or hash spill, or a report that should hit a summary table.

What is a vector, and why would you store vectors in SQL Server rather than a dedicated vector database?

A vector (embedding) is a list of floats produced by an AI model that represents meaning; similar items have nearby vectors. Storing them in SQL Server keeps them next to the business data, so you can filter by structured columns and join to products or customers in one query; apply the same security (RLS, permissions), backup, HA and DR; and avoid syncing two systems. A dedicated vector DB may still win for very large scale (hundreds of millions of vectors), very high query rates or specialized features.

Exact vs approximate vector search: when do you use each?

Exact (k-NN with VECTOR_DISTANCE and ORDER BY) compares the query vector to every candidate row. It's 100% accurate and fine for small sets or when a structured filter narrows candidates to thousands. Approximate (ANN with a DiskANN vector index and VECTOR_SEARCH) walks a graph and returns very close results much faster at millions of rows, trading a little recall. Measure recall against exact search on a sample before choosing.

Cosine, Euclidean or dot product: which distance metric?

Use the metric the embedding model was trained for. Most text embedding models (OpenAI and similar) are trained for cosine similarity. Their vectors are normalized, so cosine and dot product give the same ranking, and dot is cheaper. Euclidean suits models where magnitude carries meaning. Cosine distance in SQL Server is 1 minus cosine similarity, so smaller means more similar.

What does CREATE EXTERNAL MODEL do and how do you secure it?

It registers an AI inference endpoint (Azure OpenAI, OpenAI, Ollama, or a local ONNX runtime) as a database object with location, API format, model type and credential. T-SQL functions such as AI_GENERATE_EMBEDDINGS ... USE MODEL then call it. Secure it with a managed identity through Azure Arc instead of API keys, grant usage permission only to the roles that need it, enable outbound REST calls (external rest endpoint enabled) only where needed, restrict network egress, and monitor cost. Local ONNX models keep data on-prem.

Explain optimized locking. What are TID locking and LAQ?

TID locking: each modified row carries the ID of the transaction that last changed it. Instead of holding X locks on every modified row until commit, the transaction holds one X lock on its own TID; row locks are taken briefly and released. Others wanting that row wait on the TID. Result: far less lock memory and almost no lock escalation. LAQ: under RCSI, an UPDATE/DELETE evaluates its predicate against the latest committed row version without locks, then takes a short U/X lock only on qualifying rows. Result: fewer blocking chains between writers. Requires ADR; LAQ also needs RCSI. Available in Azure SQL first, then SQL Server 2025.

Does optimized locking remove deadlocks?

No, it reduces them. Deadlocks from lock escalation and from writers scanning past non-matching rows drop a lot. Deadlocks from true conflicts (two transactions updating the same rows in opposite order, or explicit locking hints) still happen. Lock hints like HOLDLOCK, UPDLOCK or SERIALIZABLE, or REPEATABLE READ, also turn off part of the LAQ benefit for those statements.

What's the native JSON type and how is it better than nvarchar(max)?

It stores JSON in a parsed binary format. Benefits: validation on insert (no invalid documents), faster reads because the text isn't parsed each time, efficient in-place updates with .modify(), and support for JSON indexes. Storage can also be smaller. Existing functions (JSON_VALUE, OPENJSON) work on it. Use it for semi-structured attributes such as retailer-specific fields, but still model frequently filtered or joined attributes as real columns.

Give practical uses of the 2025 regex functions in data engineering.
  • Validation: email, phone, postal code, GTIN/UPC formats with REGEXP_LIKE in CHECK constraints or DQ checks.
  • Cleansing: strip non-digits from phone numbers or remove noise words with REGEXP_REPLACE.
  • Extraction: pull pack size ("500ml", "12oz") or promo codes out of free text with REGEXP_SUBSTR.

CES means no polling jobs or change tables to clean up, and event-driven consumers. CDC is mature, works on older versions and lets you query change history in SQL. CES was preview at GA; choose it for event-driven architectures and microservices.

What does optimized sp_executesql solve?

Compilation storms. What is PBKDF2 hashing in 2025 and why does it matter?

It's a compliance improvement (NIST guidance). The trade-off is slightly more CPU per SQL login, which matters only for apps that open huge numbers of non-pooled connections.

Chapter 04 · Engine & performance

Database engine internals

Everything SQL Server stores lives on 8 KB pages, grouped in 64 KB extents. Changes are written to the transaction log first (write-ahead logging) and to data files later by checkpoint. Data is read into the buffer pool in memory and worked on there. SQLOS schedules work on one scheduler per CPU. Almost every performance or recovery question comes back to these four ideas.

Storage structures

  • Page: 8 KB with a 96-byte header. Rows up to 8,060 bytes in-row; larger variable-length values move to row-overflow pages; (max) types and XML go to LOB pages when large.
  • Extent: 8 pages. Uniform extents belong to one object; mixed extents are shared. Since 2016, user databases use uniform extents by default (MIXED_PAGE_ALLOCATION OFF).
  • Allocation pages: GAM (free extents), SGAM (mixed extents with free pages), PFS (page free space, every 8,088 pages), IAM (which extents belong to an object), DCM (changed since last full backup, used by differentials), BCM (changed by minimally logged operations).
  • Heap vs clustered index: a heap has no order; updates that grow a row can leave forwarding pointers. A clustered index is a B+tree whose leaf level is the data, ordered by the clustering key. Nonclustered indexes point to the clustering key (or to the RID on a heap).
  • Ghost records: deleted rows are first marked as ghosts and later removed by the ghost cleanup task.

Logging and recovery

  • Write-ahead logging: a log record must be hardened to disk before the matching data page is written, and before COMMIT returns. That's why log write latency (WRITELOG waits) directly limits OLTP throughput.
  • Checkpoint writes dirty pages to data files to shorten recovery. Since 2016, new databases use indirect checkpoint with TARGET_RECOVERY_TIME = 60 seconds. The lazy writer frees buffers under memory pressure.
  • Crash recovery has three phases: analysis, redo (replay committed work from the oldest dirty page), undo (roll back uncommitted work). Without ADR, a long-running transaction means a long undo.
  • Accelerated Database Recovery (2019+): keeps row versions in a persistent version store inside the user database, so rollback is a logical revert (instant), recovery time doesn't depend on the longest transaction, and the log can truncate even with long transactions open. Costs: extra space in the data files and some write overhead.
  • VLFs: the log is divided into virtual log files. Too many VLFs (thousands, from small autogrowths) slows recovery, AG redo and restore. Size the log up front and grow in large fixed amounts.
  • Log reuse: check sys.databases.log_reuse_wait_desc: LOG_BACKUP, ACTIVE_TRANSACTION, REPLICATION, AVAILABILITY_REPLICA, ACTIVE_BACKUP_OR_RESTORE, OLDEST_PAGE, XTP_CHECKPOINT.
  • Recovery models: FULL (point-in-time restore, needs log backups), BULK_LOGGED (minimal logging for bulk operations, no point-in-time restore inside a log backup that contains them), SIMPLE (log truncates at checkpoint, no log backups).

Memory and CPU (SQLOS)

  • Buffer pool caches data pages. Plan cache keeps compiled plans. Query workspace memory gives memory grants to sorts and hashes; when grants run out you get RESOURCE_SEMAPHORE waits.
  • Set max server memory to leave room for the OS and other processes; consider lock pages in memory on dedicated servers.
  • Schedulers: one per logical CPU. Work is cooperative: a task runs for a quantum of 4 ms then yields (SOS_SCHEDULER_YIELD). Time spent waiting for CPU after the resource is ready is signal wait. Running out of worker threads gives THREADPOOL waits.
  • Locks protect logical data for transactions. Latches are short physical locks that protect in-memory pages (PAGELATCH = in memory, PAGEIOLATCH = waiting for I/O). Spinlocks protect tiny internal structures and spin rather than sleep.

tempdb

tempdb holds user objects (#temp tables, table variables), internal objects (sort and hash spills, spools, work tables, DBCC) and the version store for RCSI/snapshot, triggers, online index builds and MARS. With ADR on a user database, that database's row versions move into its own persistent version store instead of tempdb.

Query compilation and plan cache

Parse → bind (algebrizer) → optimize → execute. The optimizer first tries a trivial plan; otherwise it runs cost-based search phases (0, 1, 2), stopping when a plan is "good enough" or time runs out (reason for early termination in the plan). Simple parameterization auto-parameterizes safe ad hoc statements; forced parameterization does it for nearly all. optimize for ad hoc workloads stores only a plan stub on first execution to save cache memory.

In-Memory OLTP in brief

Memory-optimized tables live fully in memory with lock-free, latch-free optimistic concurrency (multi-version). Indexes are hash (point lookups; size BUCKET_COUNT at 1-2x distinct keys) or range (Bw-tree). Natively compiled procedures turn T-SQL into machine code. Durability is SCHEMA_AND_DATA (logged, checkpoint file pairs) or SCHEMA_ONLY (lost on restart, great for staging and session state). Memory-optimized table variables are a strong replacement for #temp tables in hot procedures.

Real-time scenarios

At 2 a.m. the order database log is 98% full and growing. Applications are starting to fail with error 9002. Walk me through your response.
  1. Check log_reuse_wait_desc for the database, and free disk on the log volume.
  2. LOG_BACKUP: the log backup job failed or isn't scheduled. Run a log backup now, then fix the job.
  3. ACTIVE_TRANSACTION: find the oldest open transaction (DBCC OPENTRAN, sys.dm_tran_database_transactions). Decide with the owner whether to kill it; without ADR the rollback may take as long as the work did.
  4. AVAILABILITY_REPLICA: a secondary is behind or disconnected. Check the redo/send queue. If a replica is down for a long time, remove the database from that replica to free the log, and reseed later.
  5. REPLICATION: the log reader agent is stopped or behind.
  6. Short term, add a second log file on another volume, or grow the log if space exists. Never switch to SIMPLE in production without understanding that it breaks the log chain.
  7. Afterwards: alert on log % used, fix the root cause, right-size the log and its growth increment, and check VLF count.
Error log shows error 824 (logical consistency, bad checksum) on a 3 TB database. What do you do?
  1. Don't restart or detach. Check msdb.dbo.suspect_pages and the error log to identify the page IDs.
  2. Run DBCC CHECKDB WITH NO_INFOMSGS, ALL_ERRORMSGS (or on a restored copy if it's too heavy for production) to see the extent of the damage.
  3. If it's in an AG, automatic page repair may already have fetched a good copy from a replica.
  4. If only a few pages are damaged in FULL recovery: page restore (RESTORE DATABASE ... PAGE = '1:12345') from the last full backup plus log backups, then a tail-log backup and restore. Little downtime.
  5. If damage is in a nonclustered index, just drop and recreate the index.
  6. REPAIR_ALLOW_DATA_LOSS is the last resort.
  7. Root cause: 823/824 usually means storage, driver or firmware problems. Involve the storage team and check for errors 825 (read retry).
Users report the server "freezes" for seconds at a time. You see THREADPOOL waits and thousands of blocked sessions. What's happening?

SQL Server has run out of worker threads. Usually one blocking head (a long transaction holding locks) causes every new request to wait, each holding a worker, until the pool is exhausted, so even new logins can't be served. Connect through the Dedicated Admin Connection (ADMIN:servername), find the head blocker (sys.dm_exec_requests blocking_session_id chains, or sp_WhoIsActive), and kill it if appropriate. Afterwards, fix the cause: long transactions, missing indexes causing scans under locks, or too-high parallelism (each parallel query uses many workers). Don't just raise max worker threads; that hides the problem.

Crash recovery after a failover takes 40 minutes for one database. How do you reduce it next time?
  • Turn on ADR: undo becomes near-instant, so long-running transactions no longer extend recovery.
  • Check VLF count (sys.dm_db_log_info); thousands of VLFs slow analysis and redo. Shrink and regrow the log in large fixed increments.
  • Confirm indirect checkpoint (TARGET_RECOVERY_TIME = 60) so redo has less work.
  • Look for the transaction pattern: huge single-transaction batch jobs should commit in chunks.
  • For AGs, watch redo queue size on secondaries, because a lagging secondary means a long redo at failover.

Interview questions

Explain write-ahead logging and why it matters for performance.

Every change is described in a log record. The log record must be on disk before the changed data page can be written and before a commit is acknowledged. Data pages are written later by checkpoint and lazy writer. So commit latency equals log write latency: slow log storage shows up as WRITELOG waits and caps transactions per second. Put logs on low-latency storage, avoid tiny transactions in loops (batch them), and consider delayed durability only where some data loss is acceptable.

What's the difference between checkpoint and lazy writer?

Checkpoint writes dirty pages to disk (keeping them in memory) to reduce crash recovery time; it runs by database, based on recovery interval or indirect checkpoint target. Lazy writer frees memory: when the buffer pool is under pressure it evicts least recently used pages, writing them first if dirty. High lazy writer activity means memory pressure; checkpoint activity is normal.

What is Accelerated Database Recovery and what are its trade-offs?

ADR keeps row versions in a persistent version store (PVS) inside the database and tracks non-versioned operations in a small in-memory log stream (sLog). Rollback becomes a logical revert using versions, so it's near-instant. Recovery time no longer depends on the longest transaction, and the log can be truncated aggressively. Trade-offs: PVS uses space in the data files, a background cleaner must keep up, and write-heavy workloads see slight overhead. It's required for optimized locking in 2025.

What are VLFs and how do you manage them?

The transaction log is internally split into virtual log files. Each growth adds VLFs (count depends on growth size and version). Many small growths create thousands of VLFs, which slows recovery, restore, AG redo and log backups. Check with sys.dm_db_log_info. Fix by shrinking the log during a quiet period and growing it back in large chunks (for example 8 GB steps). Prevent it by pre-sizing the log and using a fixed MB growth, not a percentage.

Locks vs latches vs spinlocks.

Locks protect logical consistency of data for the length of a transaction and follow isolation levels (visible in sys.dm_tran_locks). Latches protect physical structures (pages in memory) for the duration of a single operation: PAGELATCH waits are in-memory contention (like tempdb allocation pages or last-page inserts), PAGEIOLATCH waits are for reading pages from disk. Spinlocks protect very small internal structures and busy-wait instead of sleeping; problems show as high CPU with backoffs in sys.dm_os_spinlock_stats.

What is the difference between a signal wait and a resource wait?

A task waiting for a resource (lock, I/O, memory) is on the waiter list: that's resource wait time. When the resource becomes available, the task moves to the runnable queue and waits for CPU: that's signal wait time. A high signal-wait percentage (often above 20-25% of total wait time) indicates CPU pressure.

What lives in tempdb, and how did ADR change that?

User objects (#temp tables, table variables, temp stored procedures), internal objects (sort/hash spills, spools, work tables for cursors and LOBs, DBCC CHECKDB) and the version store (RCSI, snapshot isolation, triggers' inserted/deleted, online index builds, MARS). With ADR enabled on a user database, row versions for that database are kept in its own persistent version store, not in tempdb, which reduces tempdb version store pressure.

Heap vs clustered index: when would you deliberately use a heap?

Heaps are good for staging tables that are bulk-loaded and then read once in full (minimal logging is easy, no sort cost), and for some append-only logging tables. Downsides: forwarding records after updates, no order, space not reclaimed after deletes without a rebuild, and every nonclustered index lookup uses an 8-byte RID. Most permanent tables should have a clustered index (or a clustered columnstore for large analytical tables).

Explain the three recovery models and when you use BULK_LOGGED.

FULL logs everything and supports point-in-time restore with log backups. SIMPLE truncates the log at checkpoint and has no log backups, so you can restore only to the last full or differential. BULK_LOGGED minimally logs bulk operations (BULK INSERT, SELECT INTO, index rebuilds) and is otherwise like FULL; a log backup containing minimally logged changes must be restored whole, so no point-in-time inside it. Use BULK_LOGGED briefly around large loads or index rebuilds on databases where you can accept that, then switch back and take a log backup. Not possible with AGs, which require FULL.

What causes error 823, 824 and 825?

823: the OS reported an I/O error when reading or writing a page. 824: the read succeeded at the OS level but SQL Server found the page inconsistent (bad checksum, torn page, wrong page ID). 825: a read failed but succeeded after retries, which is an early warning. All three usually point to storage subsystem problems. Use PAGE_VERIFY CHECKSUM, backups WITH CHECKSUM, regular DBCC CHECKDB and alerts on these errors.

What is the Dedicated Admin Connection and when do you use it?

A reserved connection with its own scheduler and memory that lets one sysadmin connect when the server is otherwise unresponsive (worker exhaustion, runaway queries). Connect with ADMIN:server in SSMS or sqlcmd -A. Enable remote DAC (remote admin connections = 1) for clustered or remote servers. Use it to find and kill blockers or runaway sessions, not for normal work.

When is In-Memory OLTP a good fit, and when is it not?

Good: very high concurrency inserts or updates with latch contention (last-page insert hot spots, session state, IoT ingestion), staging tables with SCHEMA_ONLY durability, replacing tempdb-heavy #temp tables with memory-optimized table variables, short OLTP procedures that can be natively compiled. Not good: large analytical scans, tables bigger than available memory, workloads needing features it doesn't support well, or teams that can't handle its operational differences (memory sizing, checkpoint files, no easy rollback of the filegroup once added).

What does "optimize for ad hoc workloads" do?

On first execution of an ad hoc statement, SQL Server caches only a small compiled plan stub. The full plan is cached only if the same statement runs a second time. This saves plan cache memory when an app sends many single-use statements. It's almost always safe to enable. If many statements differ only by literals, consider forced parameterization or fixing the app to use parameters.

Explain row-overflow and LOB storage, and what it means for performance.

A row's in-row size can't exceed 8,060 bytes. Variable-length columns (varchar/nvarchar/varbinary up to 8000) that push it over are moved to row-overflow pages with a 24-byte pointer left in-row. (max) types and XML are stored in-row if small enough (default up to 8,000 bytes) or on LOB pages. Reading off-row data costs extra I/O. Keep wide text out of hot tables, use large value types out of row where scanning the main row is common, and don't SELECT * across LOB columns.

What is the version store used for?

It holds previous versions of rows for RCSI and snapshot isolation readers, the inserted/deleted pseudo tables for AFTER triggers, online index builds, MARS, and readable AG secondaries (which map reads to snapshot isolation). Long-running snapshot transactions stop version cleanup and make it grow. Monitor sys.dm_tran_version_store_space_usage (and PVS size with ADR).

How does SQL Server handle NUMA?

SQLOS creates a memory node and scheduler group per NUMA node and tries to keep a connection's work and memory local. Soft-NUMA (automatic since 2016) splits large hardware NUMA nodes (more than 8 cores) into smaller ones, improving scalability of some internal structures. For MAXDOP, Microsoft's guidance is to stay within a NUMA node (no more than 8 for most servers).

Indexing strategies and columnstore

An index is a sorted copy of some columns that lets SQL Server jump to rows instead of reading the whole table. Rowstore indexes (B-trees) are for finding a few rows fast: OLTP. Columnstore indexes store each column separately and compressed: perfect for scanning and aggregating millions of rows, the warehouse. Every index speeds up some reads and slows down every write, so the architect's job is to choose the smallest set of indexes that serves the real workload.

Clustered key design

The classic rule: narrow, unique, static, ever-increasing. Narrow because the key is copied into every nonclustered index. Unique to avoid the hidden 4-byte uniquifier. Static to avoid moving rows. Ever-increasing to avoid page splits.

  • The downside of ever-increasing keys at very high insert rates is last-page insert contention (PAGELATCH_EX on the last page). Fixes: OPTIMIZE_FOR_SEQUENTIAL_KEY = ON (2019+), In-Memory OLTP, or a hash-partitioned key.
  • GUID keys (NEWID) spread inserts and cause page splits and fragmentation, and they are 16 bytes wide. NEWSEQUENTIALID or a bigint identity with a separate unique GUID column is usually better. Random GUIDs are sometimes chosen on purpose to spread hot inserts.
  • Choose the clustered key for the most important range access (for example (CustomerId, OrderDate) in an orders table read by customer), not automatically the primary key.

Nonclustered index design

  • Key column order: equality columns first, then range or sort columns. Only the leading column has a histogram.
  • INCLUDE columns cover the SELECT list without making the key wide. Covering removes key lookups.
  • Filtered indexes (WHERE Status = 'Open') are small and precise. Watch for: required SET options, parameterized queries that can't match the filter, and the stats on them updating less often.
  • Indexed views pre-aggregate and need SCHEMABINDING and COUNT_BIG(*). Enterprise can match them automatically; other editions need WITH (NOEXPAND). They add write overhead.
  • Index foreign keys used in joins and cascades.
  • Use sys.dm_db_index_usage_stats to find unused indexes (reads vs writes since restart) and the missing index DMVs as hints, not orders: they ignore column order subtleties and overlap.

Maintenance: a modern view

On SSD and SAN storage, logical fragmentation matters much less than it did with spinning disks. What still matters: page density (half-empty pages waste memory and I/O), statistics freshness, and columnstore rowgroup health. A modern standard is: update statistics often, rebuild or reorganize rowstore indexes only on real page-density problems or for specific large range-scan tables, use ONLINE = ON and RESUMABLE = ON where licensed, and maintain columnstore based on deleted rows and rowgroup size. Ola Hallengren's scripts or Azure SQL automatic tuning are the usual tooling.

Data compression

Row compression stores fixed-length types in variable length; low CPU cost. Page compression adds prefix and dictionary compression per page; more savings, more CPU on writes. Use page compression for large, read-mostly tables and indexes; row compression for busy OLTP tables. Estimate with sp_estimate_data_compression_savings. Compressed pages stay compressed in the buffer pool, so you fit more data in memory.

Real-time scenarios

An order table with 400 million rows has 22 nonclustered indexes. Inserts are slow and the nightly load misses its window. How do you rationalize it?
  1. Pull sys.dm_db_index_usage_stats (seeks, scans, lookups vs updates) over a full business cycle; persist snapshots because it resets on restart.
  2. Find duplicates and overlaps: indexes whose keys are a left-prefix of another ((A) vs (A,B)), or identical keys with different INCLUDEs that can be merged.
  3. Check Query Store for which queries use each index before removing it.
  4. Disable (not drop) candidates first, so re-enabling means a rebuild instead of a redesign; watch for regressions; then drop.
  5. For the load: drop or disable remaining nonclustered indexes during the bulk load and rebuild after, or load into a staging table and use partition switching.
  6. Agree an index governance rule: every new index needs a reason, an owner and a review.
An insert-heavy telemetry table shows high PAGELATCH_EX waits on one page. Inserts are capped at ~8,000 per second.

Last-page insert contention: all inserts hit the right-most page of an identity-keyed clustered index. Options in order of effort: OPTIMIZE_FOR_SEQUENTIAL_KEY = ON (2019+; controls the rate threads enter the latch, often a large gain with no code changes); change the clustered key to lead with a spread value (for example a hash bucket or device ID); hash-partition the table on a computed bucket column; or move the hot ingestion table to In-Memory OLTP and offload to disk in batches.

A 2 TB fact table with a CCI is getting slower each month. Queries filter by date. What do you check?
  • Rowgroup health: many small or trimmed rowgroups (loads in small batches, memory pressure during compression), open delta stores, high deleted-row percentages from updates.
  • Segment elimination on the date column: if data isn't arriving in date order, each segment covers the full date range. Use partitioning by date and/or an ordered CCI, then rebuild old partitions.
  • Dictionary pressure from wide string columns; move them to a dimension.
  • Stats freshness on the CCI.
  • Fixes: reload in 102,400+ row batches, REORGANIZE with COMPRESS_ALL_ROW_GROUPS, partition-level rebuilds, COLUMNSTORE_ARCHIVE on old partitions.

Interview questions

How do you choose a clustered index key?

Aim for narrow, unique, static and increasing, then adjust for the access pattern. If most queries read ranges for one entity (orders by customer), clustering on (CustomerId, OrderDate, OrderId) may beat an identity. Consider write patterns (hot spots vs page splits), the cost of copying the key into every nonclustered index, and how partitioning will align with it.

What's the difference between key columns and INCLUDE columns?

Key columns are sorted and stored at every level of the B-tree, so they support seeks, ordering and uniqueness. INCLUDE columns are stored only at the leaf level, so they cover queries without increasing key size and aren't limited by the 900/1,700-byte key size limit or the 32-column key limit. Put filter and sort columns in the key, and SELECT-only columns in INCLUDE.

What is a key lookup, and when is it acceptable?

A nonclustered index seek finds rows, then for each row SQL Server fetches the remaining columns from the clustered index (one random read per row). For a handful of rows it's fine. For thousands it's expensive, and the optimizer may prefer a full scan (the "tipping point"). Fix by covering the query with INCLUDE columns, as long as the index doesn't get too wide.

What are filtered indexes and their gotchas?

A nonclustered index with a WHERE clause covering only a subset of rows (for example open orders, or non-NULL values). Smaller, cheaper to maintain, with more accurate stats. Gotchas: queries must match the filter at compile time, so a parameterized predicate (Status = @s) may not use it; specific SET options (ANSI_NULLS, QUOTED_IDENTIFIER, etc.) are required for DML on the table; MERGE statements can fail on them; auto stats updates trigger on the whole table's modification counter, so filtered stats can go stale.

Explain columnstore rowgroups, delta store and the tuple mover.

Columnstore data is divided into rowgroups of up to about 1 million rows, each column compressed into a segment. Trickle inserts land in a delta store (a B-tree). When a delta store reaches 1,048,576 rows it's closed, and the background tuple mover compresses it. Bulk loads of 102,400+ rows per batch skip the delta store. Deletes mark rows in a deleted bitmap; updates are delete plus insert. Many small rowgroups or many deleted rows degrade performance until a reorganize or rebuild.

What is batch mode and how do you get it?

Batch mode processes rows in batches (roughly 900 at a time) through vectorized operators, which cuts CPU for scans, aggregates, joins and window functions by large factors. Before 2019 you needed a columnstore index in the query. From 2019 at compat 150, batch mode on rowstore can kick in for analytical queries on large rowstore tables (Enterprise). An old trick before 2019 was a dummy empty filtered NCCI on the table.

When would you use an NCCI on an OLTP table?

For real-time operational analytics: dashboards and aggregates directly on the OLTP table without ETL. The NCCI is maintained with the rowstore. Use COMPRESSION_DELAY (for example 60 minutes) so frequently updated recent rows stay in the delta store, and a filtered NCCI to cover only closed or older rows. Watch write overhead and plan stability for OLTP queries.

How do you identify unused and missing indexes, and what are the pitfalls?

Unused: sys.dm_db_index_usage_stats shows user seeks/scans/lookups vs updates; it resets on restart, so collect over time and include month-end. Missing: sys.dm_db_missing_index_details and the plan's missing index hints, or the 2019+ sys.dm_db_missing_index_group_stats_query. Pitfalls: missing-index suggestions ignore existing similar indexes, don't think about column order or INCLUDE bloat, and suggest one index per query. Consolidate them, and validate with Query Store.

Rebuild vs reorganize: what's the difference?

Rebuild creates a new copy of the index: removes all fragmentation, restores fill factor, updates statistics with a full scan, can be online (Enterprise) and resumable (2017+), and needs extra space and log. Reorganize defragments the leaf level in place, is always online, can be stopped at any time, doesn't update statistics, and is lighter but slower on heavily fragmented indexes. For columnstore, reorganize merges and compresses rowgroups; rebuild recompresses everything.

Does index fragmentation still matter on SSDs?

Less than before. Logical fragmentation hurts read-ahead for large range scans on spinning disks; on SSDs random reads are cheap. What still matters is page density: a 50% full index uses twice the memory and I/O. Rebuilds also refresh statistics, which is often the real reason "rebuilding fixed it". So measure page density and stats, and don't rebuild blindly on fragmentation percentage alone.

How do you choose a fill factor?

Default 100 (0) is right for increasing keys and read-mostly tables. For indexes with random inserts (GUID keys, natural keys) a lower fill factor (90-95) reduces page splits, at the cost of more pages to read. Set per index, not server-wide, and verify with page split counters (LOP_DELETE_SPLIT in the log or the Extended Events page_split event) and page density.

What are hash indexes on memory-optimized tables and how do you size them?

A hash index is an array of buckets pointing to row chains; it's great for equality lookups on the full key and useless for range scans or partial-key lookups. Set BUCKET_COUNT to about 1-2 times the expected number of distinct key values. Too low causes long chains; too high wastes memory. Use range (Bw-tree) indexes for ranges and ordering.

What is OPTIMIZE_FOR_SEQUENTIAL_KEY?

A 2019 index option for last-page insert contention. It doesn't remove the hot page; it controls the flow of threads trying to get the latch so the thread holding it can finish quickly, improving throughput under high concurrency. It may show a new wait type, BTREE_INSERT_FLOW_CONTROL. It helps most when many sessions insert into an identity or date-keyed index.

Indexed views: benefits and costs?

An indexed view materializes the result (often an aggregate) with a unique clustered index, so queries get pre-computed results. Requirements: SCHEMABINDING, deterministic expressions, COUNT_BIG(*) with GROUP BY, specific SET options, no outer joins. Enterprise can use it automatically; other editions need NOEXPAND. Every insert/update/delete on base tables must maintain it, which can cause blocking on hot aggregate rows. Good for read-heavy reporting on slowly changing data.

Row vs page compression: when do you use each?

Row compression stores fixed-length data in variable length (for example an int holding 5 uses 1 byte). It has small CPU cost and suits busy OLTP tables. Page compression adds column-prefix and page-dictionary compression; savings are higher (often 50-70%) but writes cost more CPU. Use it on large, mostly-read tables, history and archive tables. Both reduce I/O and memory because pages stay compressed in memory. Estimate first.

Chapter 06 · Engine & performance

Partitioning

Partitioning splits one large table into pieces by a column, usually a date, while queries still see one table. The main benefit is manageability: load a month by switching it in, delete a year by switching it out or truncating it, rebuild or compress only old pieces, and back up read-only history less often. It helps query speed only when queries filter on the partition column (partition elimination). It is not a replacement for good indexes.

Moving parts

  • Partition function: boundary values. RANGE RIGHT means the boundary value belongs to the partition on its right (the usual choice for dates: '2026-10-01' starts October).
  • Partition scheme: maps partitions to filegroups (often all to one filegroup; separate filegroups allow piecemeal restore and read-only history).
  • Aligned indexes: indexes partitioned on the same function. Required for SWITCH. The partition column must be part of every unique index key.
  • SWITCH: a metadata-only move of a whole partition between tables with identical structure, indexes, constraints and filegroup. Instant, regardless of size.
  • Sliding window: each period, SPLIT a new empty partition at the end and SWITCH OUT and MERGE the oldest one. Always split and merge empty partitions; splitting a populated partition moves data and is fully logged.
  • Limits and features: up to 15,000 partitions; TRUNCATE TABLE ... WITH (PARTITIONS (1 TO 3)) (2016); single-partition online rebuild (2014); incremental statistics; LOCK_ESCALATION = AUTO for partition-level escalation; partitioning in all editions since 2016 SP1.
CREATE PARTITION FUNCTION pfMonth (date)
AS RANGE RIGHT FOR VALUES ('2026-08-01','2026-09-01','2026-10-01','2026-11-01');
CREATE PARTITION SCHEME psMonth AS PARTITION pfMonth ALL TO ([PRIMARY]);

CREATE TABLE dbo.FactSales
( SaleDate date NOT NULL, StoreKey int NOT NULL, ProductKey int NOT NULL,
  Units int NOT NULL, NetSales decimal(18,2) NOT NULL ) ON psMonth(SaleDate);
CREATE CLUSTERED COLUMNSTORE INDEX CCI_FactSales ON dbo.FactSales ON psMonth(SaleDate);

ALTER TABLE stg.FactSales_202611 WITH CHECK

-- retire the oldest month

Real-time scenarios

Deleting one month (300 million rows) from a 5-year sales table takes 9 hours and fills the log. Fix it permanently.

Partition the table by month on the sale date with aligned indexes. Then retiring a month is TRUNCATE TABLE ... WITH (PARTITIONS (n)) or a SWITCH to an archive table (both metadata-only, seconds, minimal log), followed by a MERGE of the now-empty boundary. Getting there: build the partitioned table alongside, move data month by month with minimal logging (or rebuild the clustered index onto the partition scheme with ONLINE = ON), then rename. Automate the sliding window in an Agent job that also creates next month's partition in advance.

After partitioning a table by date, some queries got slower. Why?
  • Queries that don't filter on the date now touch every partition. A seek becomes one seek per partition.
  • The clustered key changed to include the date, so nonclustered indexes got wider or lost uniqueness.
  • Implicit conversions on the partition column (for example comparing a date column with a datetime or string parameter) prevent static elimination.
  • Non-aligned indexes were dropped to allow switching, losing access paths.
  • Fixes: make sure queries filter on the partition column, check plans for "Actual Partitions Accessed", match data types exactly, and keep a non-aligned index only where switching isn't needed for that table.
Monthly SPLIT RANGE ran for hours and blocked everything. What went wrong?

The split happened on a partition that already had data. Usually, the job missed a month, so the "future" partition (the last one with RANGE RIGHT) already held new rows. SQL Server had to physically move rows, fully logged, under a schema lock. Rule: always keep at least one empty partition at the end, and split ahead of time (create partitions months in advance). Monitor that the last partition is empty, and alert if not.

Interview questions

Is partitioning a performance feature?

Mostly a manageability feature: fast loads and deletes by switching, partition-level maintenance and compression, piecemeal restore and read-only filegroups. Performance improves when queries filter on the partition key (elimination) and when large scans run in parallel across partitions. It can hurt queries that don't filter on the key. Good indexing usually matters more for OLTP lookups.

RANGE LEFT vs RANGE RIGHT?

It defines which side of the boundary the boundary value belongs to. With RANGE RIGHT and boundary '2026-10-01', that date belongs to the partition on the right, so each partition starts on the first of the month, which is intuitive for dates. With RANGE LEFT you'd use the last value of each period, which gets messy with datetime precision. For dates use RANGE RIGHT.

What are the requirements for partition SWITCH?

Source and target must have identical columns (names, types, nullability, order), identical clustered and nonclustered indexes (aligned), the same filegroup for the partition involved, and the target partition or table must be empty. When switching a standalone table into a partition, it needs a trusted CHECK constraint that proves all rows fit the partition's boundaries. No full-text indexes or certain foreign key setups on the involved tables. Use WAIT_AT_LOW_PRIORITY to avoid being blocked by long readers.

What is a sliding window and how do you automate it?

A pattern for time-based tables: keep N periods of data. Each period you add an empty partition for the future (set NEXT USED filegroup, then SPLIT), load new data (SWITCH IN from staging), and remove the oldest period (SWITCH OUT to an archive table or TRUNCATE WITH PARTITIONS, then MERGE the empty boundary). Automate in an Agent job or pipeline with checks: the last partition is empty before split, row counts match after switches, and alert on failure.

What's an aligned index and why does it matter?

An index partitioned with the same function and column as the table (it may use a different but equivalent scheme). Aligned indexes allow SWITCH and partition-level maintenance. A non-aligned index (for example a unique index without the partition column) blocks switching. For a unique constraint on a business key that doesn't include the date, you either add the date to the key or accept a non-aligned index and lose switching.

What are incremental statistics?

Statistics created with INCREMENTAL = ON on a partitioned table keep per-partition stats and merge them into the table-level histogram. When one partition changes, you update just that partition's stats (UPDATE STATISTICS ... WITH RESAMPLE ON PARTITIONS(n)) instead of the whole table. Note that the optimizer still uses the merged table-level histogram (max 200 steps), not per-partition histograms.

Partitioned tables vs partitioned views?

A partitioned view is a UNION ALL view over separate tables with CHECK constraints on the partition column; the optimizer eliminates tables that can't match. It works in every edition, allows different indexes per member table, and can span servers (distributed partitioned views). Partitioned tables are simpler to manage (one object, SWITCH, aligned maintenance). Partitioned views are still handy for combining an internal table with an external Parquet archive.

How does partitioning help backup and restore of a very large database?

Put older partitions on separate filegroups, mark them read-only after the period closes, and back them up once. Daily backups then cover only read-write filegroups (partial or filegroup backups). In a disaster, piecemeal restore brings the primary and current filegroups online first so the business can work, then restores history filegroups later (online piecemeal restore is Enterprise).

What partition count is too many?

The hard limit is 15,000. Practical problems start well before: more compile time, memory and metadata overhead, and for columnstore, small rowgroups if each partition has too few rows (aim for multiples of 1 million rows per partition). Daily partitions over 10 years (3,650) are often too fine; monthly is common. In Synapse, remember there are already 60 distributions per partition.

How do you partition an existing large table online?

Rebuild its clustered index on the partition scheme with DROP_EXISTING = ON, ONLINE = ON (Enterprise), and rebuild nonclustered indexes aligned. For very large tables or Standard edition, create a new partitioned table, copy data in batches (oldest months first, minimally logged where possible), keep the tail in sync with triggers or CDC, then do a short cutover with sp_rename. Test log and tempdb space needs first.

Query optimizer, Intelligent Query Processing and Query Store

The optimizer guesses how many rows each step of a query will return (cardinality estimation) using statistics, then picks the cheapest plan for that guess. Most bad plans come from a bad guess: stale statistics, a parameter value that isn't typical, or a query written so the optimizer can't use an index. IQP is a family of features that let the engine correct itself during or after execution. Query Store is the flight recorder that keeps plans and runtime stats over time, so you can see when a query changed and force the good plan back.

Statistics

  • Each statistics object has a header, a density vector (for all column prefixes) and a histogram of up to 200 steps on the first column only.
  • Auto update threshold: legacy 20% + 500 rows; at compat 130+ a dynamic threshold of about SQRT(1000 × rows), so a 100-million-row table updates after ~316,000 changes instead of 20 million.
  • AUTO_UPDATE_STATISTICS_ASYNC: the query uses the old stats while the update runs in the background. Avoids compile stalls on big tables.
  • Sample rates: default sampling can miss skew. Use FULLSCAN or a higher sample for key columns and PERSIST_SAMPLE_PERCENT = ON so auto-updates keep it.
  • Ascending key problem: new dates beyond the last histogram step get poor estimates. CE 120+ handles it better; frequent stats updates on load tables help.

  • Captures query text, plans, runtime stats (duration, CPU, reads, memory, DOP) and wait stats in time intervals, stored inside the user database so it survives restarts and travels with backups.

  • Query Store hints (2022): add OPTION hints by query_id.

       SUM(rs.avg_cpu_time * rs.count_executions) / 1000 AS total_cpu_ms

Reading plans: what to look at first

  1. Estimated vs actual rows at each operator, from right to left. Big gaps point to the root cause.
  2. Warnings: implicit conversion, spills, missing statistics, no join predicate, excessive grant.
  3. Expensive scans where a seek is expected; key lookups executed many times.
  4. Residual predicates on seeks (rows read vs rows returned).
  5. Parallelism skew (one thread doing all the work) and repartition streams.
  6. Join type vs row counts: nested loops over millions of outer rows is a red flag.
  7. Memory grant vs used memory; "reason for early termination" in the root properties.

Real-time scenarios

A procedure ran in 2 seconds for months and today runs in 4 minutes. No code was deployed. Your process?
  1. Query Store: did the plan change? Compare the old and new plan IDs and their stats on the Regressed Queries report.
  2. If yes and the old plan is better, force it right away to restore service.
  3. Find why the plan changed: auto stats update with a new sample, a recompile with an atypical parameter (sniffing), an index dropped or rebuilt, a data distribution change (a new very large customer), a memory grant or parallelism change.
  4. Fix the cause (stats sample, index, rewrite, hint) so you don't depend on forcing forever, then unforce and observe.
  5. If no plan change: look at waits (blocking, I/O, CPU pressure from something else), and at row-count growth.
An Entity Framework application sends WHERE ProductCode = @p0 with @p0 nvarchar(4000), but ProductCode is varchar(20). The table has 80 million rows. What's happening?

Comparing varchar to nvarchar converts the column side (nvarchar has higher data type precedence), producing CONVERT_IMPLICIT on the column. Depending on collation, the optimizer may still seek with a range (SQL collations can't, Windows collations can do a dynamic seek), but often it scans 80 million rows. The right fix is in the app: map the property as varchar(20) (EF HasColumnType or IsUnicode(false)) so the parameter type matches. Hints and plan guides can't change a parameter's data type. If the app truly can't change, the database-side option is to change the column to nvarchar, which costs space and a large rebuild.

Month-end close reports spill to tempdb and saturate the disk. Memory grant warnings appear in plans.
  • Spills come from underestimated rows: the grant was too small for the sort or hash. Find the operator with the bad estimate and the reason (stale stats on recently loaded data, a multi-statement TVF, a table variable).
  • Update statistics after the month-end load, before reports run (add it to the ETL).
  • At compat 150+, memory grant feedback corrects repeating queries; on 2022 it persists in Query Store.
  • Rewrite: aggregate early, avoid SORT on wide rows, add an index that provides order.
  • Move the reports to a columnstore table or summary table if they scan billions of rows.
CPU is at 95% and the top wait is CXPACKET. Developers want to set MAXDOP 1 server-wide. Your view?

MAXDOP 1 server-wide kills large reporting and maintenance queries. Look first at what's parallel: often many medium OLTP queries go parallel because cost threshold for parallelism is still at the default 5. Raise it to 30-50, set MAXDOP to the Microsoft guidance (up to 8, within a NUMA node), and find the top CPU queries in Query Store. Many will have missing indexes or bad estimates that make them look expensive. CXCONSUMER is mostly harmless; CXPACKET with skew points to bad estimates. On 2022/2025, DOP feedback can tune per query. Use Resource Governor or database-scoped MAXDOP for mixed workloads.

Interview questions

What is parameter sniffing? Is it bad?

When a parameterized query or procedure compiles, the optimizer uses the actual parameter values to estimate rows and builds a plan, which is then reused. Usually that's good (saves compiles, plans fit typical values). It becomes a problem when data is skewed and the first value is atypical. Fixes: PSP (2022), OPTION(RECOMPILE), OPTIMIZE FOR (@p = value) or UNKNOWN, Query Store plan forcing or hints, splitting procedures, or a better index so one plan works for all.

What does SARGable mean? Give examples.

Search ARGument-able: a predicate the optimizer can use to seek an index. Non-sargable patterns: functions on the column (YEAR(d) = 2026, LEFT(code,3) = 'ABC', ISNULL(col, 0) = 0), math on the column (Price * 1.1 > 100), leading wildcards, implicit conversions on the column. Rewrite with the bare column on one side: date ranges, LIKE 'ABC%', col = 0 OR col IS NULL, or a persisted computed column with an index.

Nested loops vs merge vs hash join: when is each chosen?

Nested loops: a small outer input with an indexed inner input; cheap startup, good for OLTP. Merge: both inputs sorted on the join key (often from indexes); efficient for large sorted sets, needs a sort otherwise. Hash: large unsorted inputs; builds a hash table on the smaller one, needs a memory grant and can spill. Adaptive joins (batch mode) decide between hash and nested loops at run time based on the actual row count from the build side.

How do you choose MAXDOP and cost threshold for parallelism?

MAXDOP guidance: for a single NUMA node with 8 or fewer logical processors, up to that count; for more, 8; with multiple NUMA nodes, no more than the logical processors per node, max 8 (16 in some large cases). Since 2019 setup recommends a value. Cost threshold default 5 is too low for modern hardware; 30-50 is a common starting point, then tune from the plan cache cost distribution. Override per database (database-scoped MAXDOP), per workload (Resource Governor) or per query.

Temp tables vs table variables vs CTEs?

Temp tables have statistics, can be indexed after creation, cause recompiles when they change a lot, and live in tempdb. Table variables have no statistics (before 2019 estimate 1 row; 2019 deferred compilation uses the actual count at first execution), don't cause recompiles, aren't affected by rollback, and are good for small sets. CTEs are just named subqueries: not materialized, and referencing one twice can evaluate it twice. Use temp tables for large intermediate results that are joined further.

What does automatic plan correction do?

With AUTOMATIC_TUNING (FORCE_LAST_GOOD_PLAN = ON) and Query Store enabled, SQL Server detects when a query's new plan is clearly slower than its previous plan (CPU-based), forces the last good plan, and keeps checking. If the forced plan isn't better, it un-forces it. Recommendations are visible in sys.dm_db_tuning_recommendations even when the option is off. It's on by default in Azure SQL Database.

What are scalar UDF inlining and its limits?

At compat 150, eligible scalar UDFs are rewritten into relational expressions inside the calling query, so they no longer run per row and no longer block parallelism. Not eligible: UDFs with loops, time-dependent functions like GETDATE, table variables, certain constructs; and some cases are excluded for correctness. Check is_inlineable in sys.sql_modules. Inlining can create very large plans for complex UDFs.

What's the difference between estimated and actual execution plans, and what is "last actual plan"?

The estimated plan is what the optimizer would do, with estimated rows only. The actual plan adds runtime information: actual rows, executions, memory used, spills, waits per query. Capturing actual plans for every query is expensive. Since 2019, lightweight profiling and LAST_QUERY_PLAN_STATS (database-scoped) let sys.dm_exec_query_plan_stats return the last actual plan for cached queries cheaply.

OPTION(RECOMPILE) vs WITH RECOMPILE on a procedure?

OPTION(RECOMPILE) recompiles one statement on each execution and enables parameter embedding: actual values are used as literals, so branches like @p IS NULL OR ... simplify. WITH RECOMPILE on the procedure recompiles all statements every time and doesn't cache a plan, which is heavier and gives less Query Store history. Prefer the statement-level hint on the problem statement only.

How do you write dynamic SQL safely and efficiently?

Use sp_executesql with typed parameters, never string concatenation of user values (SQL injection). Concatenate only identifiers you validate (with QUOTENAME against sys.objects). Parameterized dynamic SQL gets plan reuse per distinct shape. It's the best pattern for optional-filter search screens. Grant permissions through signed procedures or EXECUTE AS when dynamic SQL needs access that the caller doesn't have.

What's the difference between CE 70 and CE 120+?

CE 70 (legacy, before 2014) assumes predicates on different columns are independent (multiply selectivities), uses simple containment for joins, and handles ascending keys poorly. CE 120+ assumes partial correlation (exponential backoff: most selective predicate fully, then square roots of the next), uses base containment for joins, and better handles values beyond the histogram. Each version after 120 tunes the model further under the compat level.

What are the Query Store operation modes and why can it go read-only?

OFF, READ_ONLY, READ_WRITE. It switches to READ_ONLY automatically when it reaches MAX_STORAGE_SIZE_MB, or on some errors. Then it stops capturing new data and your history goes stale. Prevent it with enough max size, size-based cleanup (AUTO), a sensible stale query threshold, CUSTOM capture mode to skip trivial queries, and monitoring of actual_state_desc vs desired_state_desc in sys.database_query_store_options.

How do you handle a query that's fast in SSMS but slow from the app?

Usually different SET options (ARITHABORT is ON in SSMS by default and OFF for many drivers), which give different plan cache entries; the app's plan was compiled with a different sniffed value. It's not ARITHABORT itself making it fast. Compare plans from the cache with the app's SET options (sys.dm_exec_plan_attributes), test with the app's parameter values, and fix the sniffing issue. Also check parameter types sent by the app.

What is an adaptive join?

A batch-mode operator (compat 140+) that delays the choice between hash join and nested loops until the build input has been read. If actual rows exceed an adaptive threshold, it continues as a hash join; otherwise it switches to nested loops using the inner index. It protects queries where the row count varies widely between executions. From 2019 it also works on rowstore through batch mode on rowstore.

When would you use plan guides today?

Rarely. On 2022+ Query Store hints cover most cases where you can't change the code. Plan guides are still an option on older versions (2016-2019) for vendor code: they attach hints or a fixed plan to a statement matched by exact text (or a template for parameterization). Downsides: fragile matching, hard to see, and they can fail silently after app changes.

Locking, isolation levels and concurrency

Isolation levels decide what a transaction can see while others are changing data. Pessimistic levels use locks: readers and writers wait for each other. Optimistic levels use row versions: readers see the last committed version and don't block writers. Most modern OLTP systems run Read Committed Snapshot (RCSI) so reports don't block order entry. Optimized locking in 2025 reduces writer-vs-writer blocking further.

Locks you should know

  • Modes: S (shared), U (update, prevents conversion deadlocks), X (exclusive), intent locks IS/IX/SIX on higher levels, Sch-S/Sch-M (schema stability/modification), key-range locks under SERIALIZABLE.
  • Hierarchy: database → table (object) → partition (HoBT) → page → row/key.
  • Lock escalation: from row/page to table (or partition with LOCK_ESCALATION = AUTO) when one statement holds about 5,000 locks on one object, or under lock memory pressure. A table lock blocks everyone.
  • Sch-M locks (ALTER TABLE, index rebuild finish, partition switch) wait behind any running query and block every new one behind them. Use WAIT_AT_LOW_PRIORITY.

Common patterns

IF @@ROWCOUNT = 0
  INSERT dbo.Inventory (Sku, DcId, OnHand) VALUES (@sku, @dc, @qty);
COMMIT;

-- Queue table: many workers, each takes a different row, nobody waits

  SELECT TOP (1) * FROM dbo.WorkQueue WITH (ROWLOCK, UPDLOCK, READPAST)

Real-time scenarios

Order entry is blocked every morning when a sales dashboard refreshes. The dashboard developers use NOLOCK "to fix it" and now numbers don't match. What's your recommendation?

Turn on RCSI for the database. Dashboard reads then see consistent committed data without taking shared locks, so they don't block or get blocked by order entry, and NOLOCK hints can be removed (NOLOCK can return uncommitted data, duplicate rows and missing rows, which is why the numbers don't match). Before enabling: size the version store (tempdb, or PVS if ADR is on), check for code that relies on blocking for correctness (read-then-update patterns need UPDLOCK), and note that enabling needs a short exclusive moment (WITH ROLLBACK IMMEDIATE in a maintenance window). Longer term, move heavy dashboards to a readable secondary or the warehouse.

Deadlocks appear several times an hour between the order insert procedure and the inventory reservation procedure. How do you investigate and fix?
  1. Get deadlock graphs from the system_health Extended Events session (xml_deadlock_report), or a dedicated XE session.
  2. Identify resources (keys, pages, objects), lock modes and statements in each process.
  3. Typical causes: the two procedures touch Orders and Inventory in opposite order; a scan takes many locks because of a missing index; a read-then-update pattern where both take S locks then try to convert to X.
  4. Fixes: access tables in the same order in both procedures; add the index so each touches only needed rows; use UPDLOCK on the initial read; keep transactions short; consider RCSI (readers no longer participate) and optimized locking on 2025.
  5. Make the app retry on error 1205, because some deadlocks will always occur.
A developer runs ALTER TABLE ... ADD column on a busy table during the day, and the whole application stops for 10 minutes. Explain and prevent.

The ALTER needed a Sch-M lock. It waited behind a long-running SELECT holding Sch-S. Every new query on that table then queued behind the waiting Sch-M request, so the app stopped even though the ALTER itself is quick (adding a nullable column or a column with a constant default is metadata-only since 2012 Enterprise). Prevent: run schema changes in a deployment window, set a short LOCK_TIMEOUT on deployment sessions and retry, use WAIT_AT_LOW_PRIORITY where supported (online index and switch operations), and check for long-running queries before deploying.

Interview questions

RCSI vs Snapshot Isolation: what's the difference?

RCSI changes the behavior of the default READ COMMITTED level for the whole database: each statement sees data as of its start. No code changes needed. Snapshot isolation must be requested by each session (SET TRANSACTION ISOLATION LEVEL SNAPSHOT) after enabling ALLOW_SNAPSHOT_ISOLATION: the whole transaction sees data as of its first read. It can raise update conflict error 3960 when it tries to modify a row changed by another transaction since it started. Both use the version store.

Why is NOLOCK dangerous?

It reads uncommitted data that may be rolled back, and because it uses allocation-order scans without locks, it can read rows twice or skip rows when pages split or move during the scan. It can also fail with error 601 (data movement). It still takes Sch-S locks, so it doesn't avoid schema blocking. It's acceptable only for rough monitoring queries. RCSI is the right fix for reader/writer blocking.

What is lock escalation and how do you control it?

When a statement holds roughly 5,000 locks on one object (or lock memory crosses a threshold), SQL Server tries to replace them with one table lock (or partition lock with LOCK_ESCALATION = AUTO). It saves memory but blocks others. Control: process large changes in batches below 5,000 rows, use partition-level escalation, set LOCK_ESCALATION = DISABLE on specific tables carefully (lock memory grows), or use optimized locking in 2025, which largely removes the need for escalation.

What is a U lock for?

An update lock is taken when reading a row that may be modified. Only one transaction can hold U on a resource, while others can still hold S. When it modifies, U converts to X. Without U, two transactions could both hold S and both try to convert to X, a classic conversion deadlock. WITH (UPDLOCK) on a SELECT makes a read-then-update pattern safe.

How does SQL Server choose a deadlock victim?

The lock monitor finds cycles every 5 seconds (more often when deadlocks are frequent). It picks the session with the lowest DEADLOCK_PRIORITY; if equal, the one cheapest to roll back (least log used). The victim gets error 1205 and its transaction is rolled back. Set a low priority on non-critical batch jobs so they lose, and make all apps retry on 1205.

Why is MERGE risky under concurrency?

Without HOLDLOCK (serializable) on the target, two sessions can both find "not matched" and both insert, causing duplicate-key errors or duplicates. MERGE has also had a long list of bugs, it fires triggers in confusing ways, and filtered indexes and indexed views add issues. For OLTP upserts many architects prefer explicit UPDATE then INSERT with UPDLOCK/SERIALIZABLE. MERGE is fine in single-threaded ETL with HOLDLOCK.

What isolation level do readable AG secondaries use?

All reads on a readable secondary are mapped to snapshot isolation, whatever the session requested, and locking hints are ignored. This avoids blocking the redo thread. It means the version store is used on the secondary, and long-running reports on the secondary can delay ghost cleanup on the primary (row versions must be kept), and can grow tempdb on the secondary.

What is the difference between blocking and deadlocking?

Blocking is normal waiting: session B waits for a lock held by A, and continues when A commits. It becomes a problem when A holds locks too long. A deadlock is a cycle: A waits for B and B waits for A, so neither can continue. SQL Server detects it and kills one. Blocking is found with sys.dm_exec_requests, sp_WhoIsActive or the blocked process report; deadlocks with the deadlock graph.

How do you capture blocking over time?

Set blocked process threshold (for example 10 seconds) with sp_configure, then capture the blocked_process_report event in an Extended Events session. Analyse with tools like the Blocked Process Report viewer or your monitoring product. Also log sp_WhoIsActive output to a table every minute, and use Query Store wait stats (the LOCK category) per query.

What is write skew under snapshot isolation?

Two transactions read overlapping data, each makes a decision based on what it read, and each updates different rows, so neither sees a conflict, yet together they break a rule. Example: two shifts each check "at least one manager on call" and each removes a different manager. Snapshot doesn't detect it because they updated different rows. Use SERIALIZABLE, UPDLOCK on the rows read, or a constraint that enforces the rule.

What are the costs of enabling RCSI?

Every update and delete stores a version (in tempdb, or the PVS with ADR) and adds 14 bytes per row for version info, which can cause page splits on first modification. Long-running statements keep old versions alive, growing the version store. Behavior changes for code that expected readers to wait. Turning it on needs exclusive access briefly. In exchange: readers don't block writers and vice versa, which usually improves concurrency a lot.

Interview questions

Describe your performance tuning methodology.

Define the problem and success measure (which process, how slow, target). Measure with waits and queues at server level to find the bottleneck class. Drill down to the top queries for that resource with Query Store or DMVs. Analyse their plans (estimates vs actuals, scans, spills). Fix the highest-impact item first (index, stats, rewrite, config). Validate against the baseline, document, and keep monitoring. Avoid changing many things at once.

Is Page Life Expectancy still a useful counter?

As a trend, yes; as a fixed threshold (the old "300 seconds") no, because that was set for 4 GB servers. A rough modern guide is around 300 seconds per 4 GB of buffer pool, and look per NUMA node (Buffer Node counter). Sudden drops show a large scan pushing pages out. Combine with Memory Grants Pending, lazy writes/sec and PAGEIOLATCH waits.

How do you measure storage latency from inside SQL Server?

Snapshot sys.dm_io_virtual_file_stats twice and compute (io_stall_read_ms delta / num_of_reads delta) and the same for writes, per file. Compare data files, log files and tempdb separately. Correlate with PerfMon Avg. Disk sec/Read and /Write and with storage-side metrics. Good modern targets: log writes ~1-2 ms, data reads under ~5-10 ms.

What's in your standard instance configuration?
  • Max server memory set (leave OS headroom), lock pages in memory on dedicated hosts, instant file initialization granted.
  • MAXDOP per guidance, cost threshold 30-50, optimize for ad hoc workloads on.
  • tempdb: multiple equal files, pre-sized, on fast storage; memory-optimized metadata if contention.
  • Backup compression and checksum defaults on, remote DAC enabled.
  • Model database sized sensibly with fixed MB growth; databases with page verify CHECKSUM, Query Store on, RCSI where appropriate.
  • Agent alerts for severity 16-25 and errors 823/824/825; database mail operator.
  • Power plan High Performance; 64 KB NTFS allocation unit for data and log volumes.
Which Extended Events sessions do you run permanently in production?

system_health (built in: deadlocks, severe errors, long latch and lock waits, memory issues); a blocked process report session; a lightweight long-running queries session (for example duration over 5 seconds, no plan capture); failed logins or security events if not covered by SQL Audit; and AlwaysOn_health on AG replicas. All with ring buffer or file targets and size limits.

How do you forecast database growth?

Use backup history (msdb.dbo.backupset.backup_size per database over months) or regular snapshots of file and table sizes. Fit a trend (linear or seasonal) and project 12-36 months, broken down by the largest tables so you can see which business process drives growth. Add known events (new markets, acquisitions, retention changes). Convert to storage (data, log, tempdb, backups with retention, replicas) and to cost.

What is a baseline and what do you put in it?

A record of normal behavior at different times (business hours, batch window, month-end): wait stats by category, key PerfMon counters (CPU, batch requests, compilations, PLE, disk latency, log flushes), top queries by resource from Query Store, database sizes, and job durations. Without it you can't say what changed. Store it in a DBA repository database and keep at least several months.

How do you load test before a big change?

Options: replay a captured workload (Database Experimentation Assistant, though it's aging; or a custom XE capture and replay), synthetic load (HammerDB TPC-C/TPC-H style), stress tools (ostress from RML Utilities), or application-level load tests (JMeter, k6). Compare results using Query Store and wait stats between old and new configurations, and test at peak plus growth volumes, not just average.

What are the signs of memory pressure?

Falling PLE and high lazy writes/sec, PAGEIOLATCH waits rising, RESOURCE_SEMAPHORE waits and Memory Grants Pending above 0, plan cache shrinking (frequent compiles), sys.dm_os_ring_buffers RESOURCE_MEMPHYSICAL_LOW notifications, and OS available memory low. Distinguish external pressure (OS or other apps) from internal (buffer pool vs grants vs cache).

CPU at 100%: what are the common root causes?

A few expensive queries (missing index, scans, bad estimates), plan regressions, excessive compilations (non-parameterized ad hoc SQL, RECOMPILE everywhere), too much parallelism, scalar UDFs, spinlock contention, or non-SQL processes. Check Query Store or sys.dm_exec_query_stats by total_worker_time, compilations per second, signal waits, and Task Manager for other processes.

High availability, disaster recovery and backup

High availability keeps the service running through a server failure in the same site (seconds to a minute). Disaster recovery brings it back in another site after losing the whole site (minutes to hours). Two numbers drive every design: RPO, how much data you may lose, and RTO, how long you may be down. Backups are the last line of defence for everything, including mistakes and ransomware, which replicas faithfully copy.

Availability Group details you must know

  • Quorum: Windows Server Failover Cluster votes decide which side keeps running. Use an odd number of votes, a cloud witness or file share witness, and dynamic quorum. DR-site nodes often get NodeWeight = 0 so a WAN outage can't take down the primary site.
  • Listener: a virtual network name. Multi-subnet listeners need MultiSubnetFailover=True in connection strings; for legacy clients set RegisterAllProvidersIP = 0 and a low HostRecordTTL.
  • Read-only routing: clients with ApplicationIntent=ReadOnly are sent to a readable secondary; load-balanced routing lists since 2016.
  • Commit modes: synchronous commit waits for the secondary to harden log (HADR_SYNC_COMMIT waits); asynchronous doesn't. REQUIRED_SYNCHRONIZED_SECONDARIES_TO_COMMIT (2017) enforces a minimum number of synced copies.
  • Health detection: FAILURE_CONDITION_LEVEL, HEALTH_CHECK_TIMEOUT, and database-level health detection (2016) to fail over when a database goes offline.
  • Seeding: automatic seeding streams the database over the network; manual seeding from backups is better for very large databases or slow links.
  • Not replicated (classic AG): logins and SIDs, Agent jobs, linked servers, credentials, server-level permissions, TDE certificates (must exist on all replicas), SSISDB needs its own AG setup. Contained AGs solve logins and jobs.
  • Queues: log send queue (data not yet sent: potential data loss) and redo queue (sent but not applied: failover time and stale reads).
  • Backups on secondaries: log and copy-only full backups (all versions with AGs), full and differential in 2025. Set backup preference and check sys.fn_hadr_backup_is_preferred_replica in jobs.

Backup and restore standard

  • Typical schedule: weekly full, daily differential, log backups every 5-15 minutes (this sets RPO for site loss when there's no replica).
  • WITH CHECKSUM, COMPRESSION, and encryption for backups leaving the data centre. Store TDE and backup certificates and keys separately, and test that you can restore them.
  • Backup to URL (Azure Blob) with striping for large databases; immutable storage and separate credentials to resist ransomware.
  • Follow 3-2-1-1-0: 3 copies, 2 media, 1 off-site, 1 immutable or offline, 0 errors on restore tests.
  • Automate restore tests (for example dbatools Test-DbaLastBackup, which restores and runs CHECKDB on another server). RESTORE VERIFYONLY is not a restore test.
  • Know tail-log backup (BACKUP LOG ... WITH NORECOVERY or NO_TRUNCATE on a damaged database), point-in-time restore (STOPAT), marked transactions (STOPATMARK) for multi-database consistency, piecemeal and page restore.
  • COPY_ONLY for ad hoc full backups so differential bases and the log chain aren't disturbed.

Design HA/DR for a 24x7 order management database: 3 TB, RPO 0 and RTO under 1 minute for a server failure, RPO under 5 minutes and RTO under 1 hour for a site loss.
  • Primary site: 2 replicas in synchronous commit with automatic failover, on separate hosts, racks or availability zones, each with its own storage. Cloud witness for quorum.
  • DR site: 1 replica in asynchronous commit (sync over WAN latency would hurt commits), NodeWeight 0 or a distributed AG if it's a separate cluster. Expected RPO is seconds; budget 5 minutes.

  • Backups: log backups every 5 minutes on the preferred secondary, fulls weekly (on the secondary on 2025), copies to immutable blob storage.
  • Operations: monitor log send queue and redo queue with alerts, quarterly DR drills with a timed runbook, rolling patching (secondaries first), and a documented forced-failover procedure with data-loss acceptance by the business.

Someone ran DELETE FROM dbo.Customer without a WHERE in production at 14:32. The AG replicated it everywhere within a second. Recover.
  1. Stop further damage: disable the job or user if it's ongoing. Don't fail over; the secondaries have the same deletion.
  2. Take a log backup now (captures everything up to the present).
  3. Restore full + diff + logs to a new database name on any server with STOPAT just before 14:32 (find the exact time from the transaction log with fn_dblog/fn_dump_dblog on the log backup, or from audit data).
  4. Copy the deleted rows back into production with INSERT ... SELECT (handle identity, foreign keys, triggers and rows changed since).
  5. If you had a delayed log shipping secondary (for example 4 hours behind), use it instead: it already holds the data.
  6. Afterwards: least-privilege access to production, change control, and consider Ledger or temporal tables for critical master data.
After a failover to the DR replica, the application can't log in, and nightly jobs didn't run. Why, and how do you prevent it?

Classic AG problem: logins and Agent jobs live in master and msdb of each instance, not in the AG. Either the logins didn't exist on the DR replica, or they existed with different SIDs, so database users are orphaned (fix with ALTER USER ... WITH LOGIN = ...). Jobs weren't created there, or they were but were disabled. Prevention: contained AGs on 2022+; otherwise create logins with the same SID and password hash (sp_help_revlogin or dbatools Copy-DbaLogin) and sync jobs automatically; make every job check "am I primary" (sys.fn_hadr_is_primary_replica) and deploy it on all replicas. Test in DR drills.

Ransomware encrypted the file servers and attackers deleted the backup share. The SQL VMs are intact but untrusted. What would have saved you, and what do you do now?

Now: isolate, involve security incident response, find the last known clean backups (offline copies, cloud immutable storage), rebuild SQL servers from clean images, restore and validate, rotate all credentials and keys, and check for persistence before reconnecting. Prevention: immutable backup storage (Azure Blob immutability policies or WORM appliances), backups written by an identity that can't delete them, an off-domain or separate tenant for backup infrastructure, offline copies, encrypted backups with keys stored separately, regular restore tests, and monitoring for mass deletion of backup files.

Synchronous AG commit latency is hurting the order API. The secondary is in another building 15 km away.

Every commit waits for the log to be hardened on the secondary: network round-trip plus secondary disk write. Check HADR_SYNC_COMMIT wait time per transaction, network latency (ping is not enough; check throughput and packet loss), and the secondary's log disk latency. Fixes: faster log storage on the secondary, network tuning, batching small transactions in the app (fewer commits), and compression settings for the AG transport. If the business allows, use synchronous only within the same building or zone and asynchronous to the other site. On SQL 2025, review the AG flow-control improvements.

Interview questions

Explain RPO and RTO and how they drive technology choices.

RPO is the maximum acceptable data loss measured in time; RTO is the maximum acceptable time to restore service. RPO 0 needs synchronous replication (sync AG or FCI with replicated storage). RPO of minutes allows async AG, log shipping or frequent log backups. RTO of seconds needs automatic failover (sync AG, FCI); RTO of hours allows restore from backup. Cost rises steeply as both approach zero, so get the business to put a value on downtime and data loss per system and tier systems accordingly.

FCI vs Availability Groups: compare them.

FCI: one copy of data on shared storage, the whole instance fails over (logins, jobs, msdb), no readable secondary, storage is a single point of failure, failover includes database recovery. AG: each replica has its own copy, database-level failover, readable secondaries, backup offload, automatic page repair, no shared storage needed, but instance-level objects must be synced (or contained AG). They can be combined: an FCI can be an AG replica, though automatic failover between FCI and AG isn't supported.

What is quorum and why do you need a witness?

Quorum is the majority of votes the cluster needs to stay online; it prevents split brain (two sides each thinking they're primary). Each node has a vote, and a witness (disk, file share or cloud witness) adds a tie-breaker vote. With an even number of nodes, losing half would otherwise stop the cluster. Dynamic quorum and dynamic witness adjust votes as nodes go down. For multi-site, remove votes from DR nodes so a WAN failure doesn't affect the primary site.

What's the difference between log send queue and redo queue?

Log send queue: log generated on the primary not yet sent to the secondary. If the primary is lost, that's data loss (for async). Redo queue: log received and hardened on the secondary but not yet applied to data files. It doesn't lose data, but it increases failover time (redo must finish before the database comes online) and makes readable secondaries stale. Monitor both in sys.dm_hadr_database_replica_states.

What's a distributed availability group and when do you use it?

An AG made of two AGs, each in its own cluster. The primary AG's primary replica forwards log to the secondary AG's primary (the forwarder), which feeds its own secondaries. Use cases: DR across regions or domains without stretching one WSFC, migrations to new hardware, OS or versions with minimal downtime (including Windows to Linux), and the basis of the MI link. Failover is manual.

What happens to data on a forced failover with async commit?

Any transactions committed on the old primary but not yet sent to the new primary are lost. After forcing, other secondaries are suspended. When the old primary returns it becomes a secondary, and its unsent transactions are rolled back when it resyncs. If those transactions matter, before resuming, you can create a database snapshot on the old primary to recover the missing changes manually.

How do you patch an AG with minimal downtime?
  1. Patch async secondaries and DR replicas first.
  2. Patch the synchronous secondary; confirm it's synchronized.
  3. Manually fail over to the patched secondary (a few seconds of downtime).
  4. Patch the old primary, which is now a secondary.
  5. Optionally fail back.

Remove the node being patched from the automatic failover partner list during patching, and check that databases resynchronize after each step.

What is MultiSubnetFailover and why does it matter?

In a multi-subnet AG, the listener has an IP address in each subnet, but only one is online. With MultiSubnetFailover=True, the client tries all registered IPs in parallel and connects to the one that answers, so failover reconnection takes seconds. Without it, clients may try the offline IP first and time out (often 20+ seconds), and DNS caching makes it worse. For clients that don't support it, set RegisterAllProvidersIP = 0 and a low HostRecordTTL.

Why do you still need backups if you have an AG with three replicas?

Replicas copy everything, including mistakes: accidental deletes, bad deployments, logical corruption and ransomware encryption done through SQL. Backups give you history and point-in-time recovery. You also need them for compliance retention, refreshing lower environments and seeding new replicas.

What is a tail-log backup?

A backup of the log records not yet backed up, taken before a restore (or when the database is damaged), so you can recover up to the moment of failure. BACKUP LOG db TO ... WITH NORECOVERY leaves the database in restoring state for a planned migration; NO_TRUNCATE (and CONTINUE_AFTER_ERROR) works when data files are damaged but the log is intact. SQL Server warns you to take one when you restore over an existing FULL-recovery database.

Log shipping: when is it still the right answer?

When you need cheap DR on Standard edition with many databases; a delayed copy (for example restore with a 4-hour delay) as protection against human error; reporting from a standby copy where being minutes behind is fine; or simple DR to a different version or Azure VM. It has no automatic failover and readers are disconnected during each restore in standby mode.

What doesn't fail over with an AG, and how do you handle it?

Logins (and their SIDs), Agent jobs, operators and alerts, linked servers, credentials and proxies, server-level permissions and roles, server audit specifications, endpoints, certificates used by TDE or backups, SSIS catalog configuration, and instance settings. Handle them with contained AGs (2022+) where possible, otherwise automated synchronization (dbatools), jobs that check if they're on the primary, and DR drills that test logins and jobs.

How do you verify that backups are good?

By restoring them. Automate regular restores of each critical database to a test server, then run DBCC CHECKDB on the restored copy, log the time taken (that's your real restore RTO), and alert on failures. Backups WITH CHECKSUM and RESTORE VERIFYONLY detect only some problems. Also verify that certificates for TDE or encrypted backups can be restored on a new server.

How do you design DR for SQL Server using Azure?

Options: an Azure VM as an async AG replica (or distributed AG) over ExpressRoute or VPN; the MI link to Azure SQL Managed Instance (SQL 2016 SP3+, with failback from 2022); log shipping or backups to Azure Blob storage with restore on demand (cheapest, slowest RTO). With SA you get a free passive DR replica in Azure. Plan networking, DNS failover, identity (Entra ID or a DC in Azure) and application tier failover too, because a database in Azure is useless if the apps can't reach it.

What are the backup options for a 50 TB database?
  • Storage or cloud snapshots with the T-SQL snapshot backup (2022+): seconds, independent of size.
  • Striped backup to multiple files or URLs with compression (ZSTD on 2025), tuned BUFFERCOUNT and MAXTRANSFERSIZE.
  • Filegroup and partial backups with read-only historical filegroups backed up once.
  • Differential backups to reduce restore chain length; offload fulls to a secondary (2025).
  • Always test the restore time; for very large databases RTO is usually dominated by restore throughput.

Data modeling: normalization, Kimball and Data Vault

Data modeling is deciding what things the business cares about, how they relate, and how to store them. Normalized models (3NF) are for systems that write a lot: each fact is stored once, so updates are safe. Dimensional models (Kimball stars) are for analysis: facts (measurements) surrounded by dimensions (context), easy and fast to query. Data Vault is for integrating many changing sources with full history and audit, then publishing stars on top.

Three levels of model

  • Conceptual: business entities and relationships, no attributes or keys. For alignment with the business ("a Retailer has many Stores; a Store sells many Products").
  • Logical: entities, attributes, keys and relationships, normalized, independent of database product.
  • Physical: tables, data types, indexes, partitioning, constraints, compression, for a specific platform.
  • Tools: erwin, ER/Studio, PowerDesigner, SqlDBM, Visual Paradigm, or code-first with dbt and diagrams generated from metadata.

Normal forms in one line each

  • 1NF: atomic values, no repeating groups (no "Phone1, Phone2, Phone3" columns or comma lists).
  • 2NF: 1NF and every non-key attribute depends on the whole key (matters for composite keys).
  • 3NF: 2NF and no non-key attribute depends on another non-key attribute ("the key, the whole key and nothing but the key").
  • BCNF: every determinant is a candidate key (stricter 3NF).
  • 4NF: no independent multi-valued facts in one table. 5NF: no join dependencies that would let you split further without loss.
  • Denormalize deliberately for read performance or simplicity, and document how consistency is kept (triggers, ETL, computed columns, indexed views).

Kimball dimensional modeling

Four-step design: 1) pick the business process (shipments, POS sales, trade promotions), 2) declare the grain (one row per SKU per store per day), 3) identify the dimensions, 4) identify the facts. The grain is the most important decision; never mix grains in one fact table.

A SaaS platform for 2,000 distributor customers needs a multi-tenant data model. What are your options?

Interview questions

What is the grain of a fact table and why is it so important?

The grain is the exact meaning of one row (for example "one row per SKU per store per day"). It defines which dimensions apply and which facts are valid, and it prevents double counting. Mixing grains (daily rows with monthly targets in one table) causes wrong totals. Declare the grain before choosing dimensions and facts, and make it as atomic as the source allows, because you can always aggregate up but can't drill below the grain.

Star vs snowflake schema?

A star has denormalized dimensions joined directly to the fact: fewer joins, simpler for users and BI tools, and the preferred model for Power BI. A snowflake normalizes dimensions into sub-tables (Product → Brand → Category): less redundancy, but more joins and complexity. Snowflaking is reasonable for very large dimensions with shared sub-levels or when an outrigger is used by several dimensions. In the semantic layer, flatten to a star anyway.

Why use surrogate keys in a warehouse?

They isolate the warehouse from source key changes and reuse, let you integrate sources with different keys, enable SCD type 2 (multiple rows per business key), allow "unknown" and "not applicable" members, and keep fact tables narrow with int joins. Keep the business (durable) key as an attribute for lookups and type 7 reporting.

How do you implement SCD Type 2 efficiently?

Compute a hash of the type 2 attributes (HASHBYTES('SHA2_256', CONCAT_WS('|', ...))) in staging. Compare with the current dimension row by business key: new keys get inserted; changed hashes close the current row (set ValidTo and IsCurrent = 0) and insert a new row; type 1 columns update in place on all rows. Do it set-based (UPDATE then INSERT, or MERGE with HOLDLOCK in a single-threaded ETL). Index the business key plus IsCurrent. Use IS DISTINCT FROM (2022) for NULL-safe comparisons if you compare columns instead of hashes.

What are conformed dimensions and the bus matrix?

Conformed dimensions have the same keys, attributes and meaning wherever they're used, so measures from different fact tables can be compared (drill-across). The bus matrix is a grid of business processes (rows) against dimensions (columns), marking which dimensions each process uses. It's the roadmap for building an enterprise warehouse incrementally, one process at a time, while staying integrated.

Explain the accumulating snapshot fact table.

One row per instance of a process with a defined start and end (an order, a claim, a promotion), with several date keys for milestones and lag measures between them. The row is updated as milestones occur. It's good for pipeline and cycle-time analysis (order-to-delivery days). It's one of the few fact types where updates are normal, so design loads accordingly.

What's a junk dimension and a degenerate dimension?

A junk dimension combines several low-cardinality flags and indicators (payment type, promo flag, order channel) into one small dimension of their combinations, keeping the fact narrow. A degenerate dimension is a dimension key with no attributes of its own, like an invoice or order number, kept directly in the fact table for grouping and drill-through.

How do you handle many-to-many relationships in a dimensional model?

Use a bridge table between the fact (or dimension) and the multi-valued dimension, with a group key and optionally a weighting factor so allocations add up to 100%. Example: a sales line linked to multiple promotions, or a product in multiple categories. Explain to users that totals can double count without weighting. In Power BI, model the bridge with bidirectional filtering carefully.

What is a late-arriving dimension and how do you handle it?

A fact arrives referencing a business key the dimension doesn't have yet (a new SKU in POS data before the product master update). Options: insert an inferred member with just the business key and an "inferred" flag, link the fact to it, then update the row (type 1 style) when the full record arrives; or park the fact in a suspense table and reprocess later. Inferred members keep totals complete, which is usually preferred.

When would you choose Data Vault?

Many source systems, frequent source changes, a need for full history and auditability (regulated industries, M&A integration), parallel teams loading at the same time, and an automation tool to generate the patterns. Avoid it for small, stable environments or teams without automation, because the number of tables and joins adds cost. It's a core integration layer; users still query marts.

Hubs, links and satellites: explain each with an example.

Hub Product: one row per unique SKU code, with hash key, load date and record source. Hub Retailer: one row per retailer GLN. Link ProductRetailer (listing): one row per unique combination of product and retailer hash keys. Satellite on Hub Product from SAP: name, brand, weight, with history (new row on any change detected by hash diff). Satellite on the link: listing status and listing date from the retailer portal. Business rules come later, in the business vault.

What are PIT and bridge tables in Data Vault?

A point-in-time table stores, for each hub key and snapshot date, the load date of the satellite row valid at that time in each satellite, so queries can equi-join instead of doing range lookups across many satellites. A bridge table pre-joins hubs and links along a common path (for example product to retailer to region) for faster querying. Both are query-assistance tables, rebuilt as needed.

Natural keys vs surrogate keys in OLTP?

Natural keys carry business meaning and avoid an extra lookup, but they can change, be wide, or be composite. Surrogate keys (identity, sequence) are stable and narrow, and simplify foreign keys. Common practice: a surrogate primary key plus a unique constraint on the natural key, so you get both stability and integrity.

Which data types do you standardize, and why?

Money as decimal(19,4) or a precision agreed with finance (not float, and the money type has rounding issues in division). Dates as date and timestamps as datetime2(3) or datetimeoffset for multi-time-zone data; store UTC. varchar for codes and ASCII data, nvarchar (or UTF-8 collation varchar on 2019+) for names in many languages. Smallest integer type that fits. Explicit NOT NULL with defaults where possible. Consistent types for the same column across tables prevent implicit conversions.

Temporal tables vs SCD Type 2?

System-versioned temporal tables (2016) automatically keep row history by system time (when the database recorded the change), with FOR SYSTEM_TIME AS OF queries. They're great for OLTP audit history and "what did the table look like on date X". SCD2 tracks business-effective time (when the change is valid in business terms), uses surrogate keys for facts and is under ETL control. Warehouses usually need SCD2; temporal tables are useful as a source for it.

Data warehouse design: SQL Server and MPP

A data warehouse is built in layers: raw copies of source data, a cleaned and integrated layer, and a presentation layer of star schemas that reports use. On SQL Server, the physical recipe is clustered columnstore fact tables partitioned by date, rowstore dimensions, set-based loads and fresh statistics. On MPP platforms (Synapse dedicated pools) the extra decision is how to spread each table across nodes so joins don't have to move data.

Physical design on SQL Server

  • Facts: clustered columnstore, partitioned monthly (or yearly for small facts), loaded in 102,400+ row batches or through partition switching. Nonclustered B-tree indexes on the CCI only for selective lookups.
  • Dimensions: rowstore with clustered index on the surrogate key, unique index on business key (+ IsCurrent), page compression.
  • Foreign keys: trusted FKs let the optimizer eliminate joins, but cost load time. Common compromise: enforce referential integrity in ETL (lookups to unknown member) and keep FKs disabled or NOCHECK, or validate after load.
  • Recovery model: SIMPLE or BULK_LOGGED for pure warehouses that can be rebuilt from staging; FULL if you need point-in-time restore or AGs.
  • Statistics: update after each load on affected partitions; CCI tables still need stats.
  • Aggregates: summary tables or indexed views for top dashboards; Power BI aggregations for huge facts.
  • Workload separation: Resource Governor for ETL vs reporting, or readable secondaries for reporting.

MPP: Synapse dedicated SQL pool

  • One control node, many compute nodes, data always split across 60 distributions. Performance depends on avoiding data movement (shuffle or broadcast) between distributions.
  • Hash distribution for large facts and big dimensions: choose a column with many distinct values, even spread, frequently used in joins and GROUP BY, not usually filtered alone, and not nullable-heavy. Joining two tables hash-distributed on the same column needs no data movement.
  • Replicated for small dimensions (under about 2 GB compressed): a full copy on each compute node.
  • Round-robin for staging tables: fastest load, but joins always move data.
  • Load with COPY INTO or PolyBase from ADLS; transform with CTAS (minimally logged, parallel) instead of UPDATE/DELETE on big tables.
  • Check skew with DBCC PDW_SHOWSPACEUSED; check movement in EXPLAIN plans and sys.dm_pdw_request_steps.
  • Workload groups and classifiers for isolation; result set caching and materialized views for dashboards.
  • Status: Synapse dedicated pools get no new features; Microsoft Fabric Warehouse is the forward path, with migration tooling.

Interview questions

How do you choose a distribution column in Synapse?

Many distinct values (far more than 60), even data spread (no skew from NULLs or default values), used in joins with other large tables and in GROUP BY, not mainly filtered on (filtering to one value would hit one distribution), and stable. Fact and large dimension tables that join often should share the distribution column. Validate skew after loading; under ~10% difference between distributions is good.

Why use CTAS instead of UPDATE or DELETE on large MPP tables?

CTAS writes a new table in parallel and is minimally logged, so it's much faster than fully logged UPDATE/DELETE on billions of rows, and it produces well-compressed columnstore rowgroups. The pattern: CTAS the corrected data into a new table, then rename (swap) tables. It also lets you change distribution or partitioning at the same time.

What's the difference between OLTP and OLAP design?

OLTP: many small concurrent reads and writes, normalized (3NF) to protect integrity, rowstore indexes for seeks, short transactions, full recovery and HA. OLAP: large scans and aggregations, few writers (batch loads), denormalized stars, columnstore, partitioning, batch mode, and query patterns that are unpredictable. Running both on one database needs care (NCCI, readable secondaries) or separation.

How do you design for near real-time reporting without hurting OLTP?

In order of latency: query a readable AG secondary (seconds behind, no ETL); an NCCI on the OLTP table with compression delay (real-time analytics on the same server); Fabric mirroring into OneLake (near real-time, separate compute); CDC or change event streaming into a streaming pipeline (Event Hubs to Eventhouse/KQL or a lakehouse). Choose based on latency need, query complexity and how much load the primary can take.

What is a semantic layer and why do architects care?

It's the business-facing model (Power BI semantic model, SSAS Tabular, or a headless BI layer) that defines measures, hierarchies, relationships and security once. Without it, every report re-implements "Net Sales" differently. It decouples users from physical tables, so you can change the warehouse underneath. Governance means certified and promoted models, deployment pipelines and naming standards.

Do you enforce foreign keys in a warehouse?

It depends on load volume and trust in the ETL. Trusted FKs give integrity and help the optimizer (join elimination), but checking billions of rows during loads is slow. Common approach: ETL guarantees integrity by mapping missing keys to an unknown member, FKs are created WITH NOCHECK or disabled during load, and a post-load validation job checks orphan counts. Document the choice.

Import vs DirectQuery vs Direct Lake in Power BI?

Import copies data into VertiPaq: fastest queries, full DAX features, but data is as old as the last refresh and limited by capacity memory. DirectQuery sends queries to the source each time: fresh data, but performance depends on the source and some DAX is limited. Direct Lake (Fabric) reads Delta tables from OneLake directly into memory: import-like speed without scheduled import refreshes; it may fall back to DirectQuery in some cases (for example certain security setups on the SQL endpoint), so design for it.

How do you handle very large fact tables in Power BI?

Incremental refresh with partitions by date (refresh only recent periods), aggregation tables for common grains, composite models with detail in DirectQuery, removing unused columns and high-cardinality text, integer keys, and on Fabric, Direct Lake over well-maintained Delta tables (V-Order, optimized file sizes). Push heavy logic to the warehouse rather than Power Query or DAX.

How do you test and reconcile a warehouse?

Row counts and control totals per load between source, staging and target; key financial totals reconciled to the source system's reports (net sales by month must equal SAP); referential checks (orphans pointing to unknown); duplicate checks on business keys; SCD checks (one current row per key); trend and anomaly checks (volume within expected range). Automate them in the pipeline (dbt tests, SQL assertions) and publish a data quality dashboard.

What is a materialized view in Synapse or an indexed view in SQL Server used for in a warehouse?

Both pre-compute aggregations or joins and are kept up to date automatically as base tables change, and the optimizer can use them for matching queries even when not referenced directly (Synapse always; SQL Server Enterprise). Use them for the dashboard queries that run all day over the same aggregates. Cost: maintenance on load, and in Synapse watch the overhead ratio (rebuild when it grows).

Loading fast in SQL Server

  • Minimal logging: bulk operations (BULK INSERT, bcp, SqlBulkCopy, INSERT...SELECT) with TABLOCK into a heap, or into an empty clustered index, in SIMPLE or BULK_LOGGED recovery. Since 2016, INSERT...SELECT with TABLOCK into a clustered index can be minimally logged for new pages.
  • Columnstore: batches of at least 102,400 rows go straight to compressed rowgroups; parallel INSERT...SELECT with TABLOCK.
  • Partition switching: load a staging table on the same filegroup with the same indexes and a check constraint, then switch in. Readers never see half-loaded data.
  • Batching large updates and deletes (for example 50,000 rows per loop) to limit log growth, lock escalation and AG redo lag.
  • Disable nonclustered indexes during big loads and rebuild after, when the load touches most of the table.

Framework principles

  • Metadata-driven: a control table lists sources, targets, load type, watermark column, schedule, and owner. One generic pipeline loops over it.
  • Idempotent and restartable: re-running a failed batch gives the same result (delete-and-insert by batch ID or partition, MERGE on keys). Checkpoints let a long run restart from the failed step.
  • Audit columns: BatchId, LoadDts, RecordSource, RowHash on every table. A batch log table records start, end, rows read/written/rejected, status.
  • Error handling: bad rows to a quarantine table with the reason, not a failed whole load (unless the error rate crosses a threshold).
  • Data quality gates: row count thresholds, NULL and range checks, referential checks before publishing to gold.
  • Security: managed identities, secrets in Key Vault, private endpoints, least-privilege service accounts.
  • Observability: alerts on failure and on SLA breach (late data), and lineage in Purview.

Real-time scenarios

The nightly ETL used to finish in 2 hours. Over 6 months it grew to 6 hours and now misses the 6 a.m. reporting SLA. How do you approach it?
  1. Get step-level timings over the 6 months from the batch log (or SSISDB execution reports, ADF run history). Find the steps whose duration grew most, and whether growth tracks data volume (linear) or jumped (a regression).
  2. For the top steps: is it a full reload that should be incremental? A lookup against a growing table without an index? A MERGE on a huge target without a supporting index? Row-by-row SSIS components (OLE DB Command)?
  3. Database side: waits during the window (log writes, tempdb, blocking with other jobs), plan changes in Query Store, stats on staging tables.
  4. Typical fixes: incremental loads with CDC or watermarks; set-based SQL instead of row-by-row; partition switch for facts; parallelise independent branches; minimal logging; scale compute only for the window.
  5. Then put an SLA alert in place that warns at 4 a.m. if the critical path is behind.
A retailer sends POS files daily, but sometimes resends corrected files for the previous 3 weeks. How do you design the load?

Make the load idempotent at the grain of the file: each file covers a known retailer and week range. Land files unchanged in bronze with file name, received time and hash. In staging, parse and validate. For the target fact, delete-and-replace by (retailer, week) for every week in the incoming file inside one transaction (or switch the affected partitions), instead of appending. Keep a file registry so the same file isn't processed twice, and keep earlier versions in bronze for audit. Report restatements so analysts know numbers changed.

CDC is enabled on 60 tables in the ERP database and the log keeps growing; log_reuse_wait_desc shows REPLICATION.

CDC uses the replication log reader. If the CDC capture job is stopped, failing or too slow, log records can't be truncated. Check that the capture job (cdc.<db>_capture) is running and look at sys.dm_cdc_log_scan_sessions and sys.dm_cdc_errors. Tune maxtrans, maxscans and pollinginterval for high volume. Make sure the cleanup job runs so change tables don't explode. Disable CDC on tables nobody consumes. For very high volume, consider Fabric mirroring or CES on 2025, or a log-based tool like Qlik Replicate.

You need to migrate 400 SSIS packages to the cloud. Options?
  • Lift and shift: deploy SSISDB to Azure SQL DB or MI and run packages on an Azure-SSIS IR in ADF. Fastest, minimal rework; you still own SSIS skills and IR cost. Use a self-hosted IR as proxy for on-prem sources.
  • Re-platform: rebuild as ADF or Fabric pipelines with SQL/dbt transformations (ELT). Most effort, best long-term.
  • Hybrid: lift and shift now, rebuild the high-value or problematic packages over time.
  • Inventory first: group packages by pattern (most are "copy table A to B" and can be replaced by one metadata-driven pipeline), complexity, and business criticality.

Interview questions

ETL vs ELT: when do you choose each?

ETL when the target can't or shouldn't do heavy transformation (an OLTP target, masking sensitive data before it lands, complex non-SQL logic) or when existing SSIS investment is large. ELT when the target is a scalable warehouse or lakehouse: load raw data quickly, keep it for replay, and transform with SQL or Spark close to the data, with version-controlled code (dbt). Most modern designs are ELT with some transformation (PII masking, format conversion) during ingestion.

CDC vs Change Tracking: compare.

Change Tracking records that a row changed (key and operation) and a version number, synchronously in the same transaction, with very low overhead; you read current values by joining back. No history of intermediate values. CDC reads the transaction log asynchronously and writes full before and after images of every change into change tables, with LSN ranges, including deletes; more overhead and storage, needs Agent (on-prem) and cleanup. Use CT for syncing current state; CDC when you need every change or deletes with old values (audit, SCD2, streaming).

What does idempotent mean in ETL, and how do you achieve it?

Running the same load twice gives the same result as running it once. Techniques: delete-and-insert by batch, date or partition; MERGE or upsert on business keys; truncate-and-load staging; tracking processed files in a registry; deterministic surrogate key lookups; and avoiding "append without checking". It makes retries and backfills safe, which is essential for automated orchestration.

Why is rowversion better than a ModifiedDate column for watermarks?

rowversion is updated automatically by the engine on every change, so no application can forget it, and it's monotonic per database. ModifiedDate depends on application code and server clocks, and both suffer from in-flight transactions: a transaction that started earlier but commits after you read can have a lower value than your new watermark and be skipped. With rowversion, use MIN_ACTIVE_ROWVERSION() as the upper bound to avoid that gap. Neither detects hard deletes.

How do you detect deletes in an incremental load?

CDC or Change Tracking (they record deletes); soft-delete flags in the source; periodic full key comparison (extract all keys and anti-join to the target), which is acceptable weekly for big tables; or source triggers writing to a delete log. In lakehouses, Delta Change Data Feed or the source's CDC stream.

What are the conditions for minimal logging?

Database in SIMPLE or BULK_LOGGED recovery; a bulk operation (BULK INSERT, bcp, SqlBulkCopy, SELECT INTO, INSERT...SELECT); a table lock (TABLOCK hint); and target structure: a heap (with or without nonclustered indexes, though index pages are fully logged), or an empty B-tree, or since 2016 new pages in a B-tree with TABLOCK. Not replicated tables. Check with fn_dblog log record counts in testing. AG databases are in FULL recovery, so you can't minimally log there.

SSIS performance: what are the main tuning levers?

Use set-based SQL where possible (ELT inside SSIS with Execute SQL). In data flows: avoid blocking transformations (Sort, Aggregate) on large sets, push sorts to the source query, use fast load with sensible rows per batch and maximum insert commit size, tune DefaultBufferMaxRows/DefaultBufferSize (or AutoAdjustBufferSize), use full-cache lookups on small reference sets, avoid OLE DB Command (row by row), run independent flows in parallel, and use the balanced data distributor for heavy transformations.

What's a metadata-driven pipeline framework?

Instead of one pipeline per table, a control table describes each load (source connection, object, query, target, load type full/incremental, watermark column, key columns, schedule, priority, active flag). A generic parent pipeline reads the control table and calls child pipelines with parameters. Adding a table means adding a row, not building a pipeline. Logging writes back to the control tables. It scales to thousands of tables and keeps patterns consistent.

How do you handle schema drift from sources?

In the raw layer, store data in self-describing formats (Parquet, Delta, JSON) and allow new columns (ADF schema drift, Auto Loader schema evolution, Delta mergeSchema). Alert on schema changes. In curated layers, apply explicit schema contracts: new columns are added deliberately, removed or renamed columns fail the pipeline with a clear message. Data contracts with source owners reduce surprises.

What's the difference between ADF's integration runtimes?

Azure IR: managed compute for copying between cloud stores and running data flows. Self-hosted IR: software you install on-prem or in a VNet to reach private sources (on-prem SQL, file shares, SAP); it's also needed for some connectors. Azure-SSIS IR: a managed cluster that runs SSIS packages in Azure. Managed VNet Azure IR offers private endpoints without a self-hosted IR for many sources.

Batch vs streaming: how do you decide?

Ask what decision depends on the data and how fast it must be made. Daily or hourly decisions (most finance and sales reporting) are fine with batch or micro-batch, which is simpler and cheaper. Streaming is for operational decisions in seconds or minutes (inventory availability, fraud, IoT alerts). Lambda architecture runs both paths; Kappa uses only a stream with replay. Many modern platforms (Spark structured streaming, Delta, Fabric Eventstream) let one code path serve both.

Why Parquet or Delta instead of CSV for data exchange and lakes?

Parquet is columnar, compressed and typed, with min/max statistics per row group, so engines read only needed columns and skip data, often 5-10x smaller and faster than CSV. Delta (and Iceberg) add a transaction log on top of Parquet: ACID writes, MERGE/UPDATE/DELETE, time travel, schema enforcement, and concurrent readers and writers. CSV has no types, no schema, quoting problems and must be read fully.

How would you load SAP data into the platform?

Use supported extraction: SAP ODP (Operational Data Provisioning) through the ADF/Fabric SAP CDC connector, SAP BW/4HANA or Datasphere extractors, SLT replication, or partner tools (Qlik, Theobald). Avoid direct table reads of SAP's database (licensing and support issues, complex table logic). Land raw extracts in bronze, map SAP codes to conformed dimensions through MDM, and reconcile financial totals with SAP reports.

  • Failover groups (SQL Database and MI): a group of databases fails over together, with stable read-write and read-only listener endpoints; automatic policy with a grace period, or customer-managed.

Security baseline

Things that surprise on-prem DBAs

  • Resource limits per tier: log write rate (MB/s), IOPS, workers and sessions, tempdb size. Heavy ETL often hits the log rate limit first (waits like LOG_RATE_GOVERNOR / INSTANCE_LOG_RATE_GOVERNOR).
  • No access to the OS or file system; restricted trace flags and sp_configure.
  • Maintenance windows and transient reconnects: apps need retry logic.
  • MI update policy: "SQL Server 2022/2025" format keeps databases restorable to on-prem SQL Server of that version; "Always-up-to-date" gets new features first but blocks restore back to on-prem.
  • Automatic tuning in SQL Database can create and drop indexes; decide whether you allow it.

An app with 120 databases, Agent jobs, cross-database joins, CLR and linked servers to Oracle must move to Azure in 6 months with minimal code change. Where do you put it?

It supports Agent, cross-database queries within the instance, CLR (SAFE assemblies, loaded from binary), linked servers (with network line of sight to Oracle) and Service Broker within the instance, so code changes are minimal. Your nightly load to Azure SQL Database General Purpose 8 vCores takes 3x longer than on-prem. Waits show LOG_RATE_GOVERNOR.

You're hitting the tier's log generation rate limit. Options: reduce log volume (batch sizes, minimal logging isn't available in Azure SQL DB FULL recovery, so load into a staging table with fewer indexes, use CCI loads in large batches, avoid unnecessary updates); scale up for the load window (more vCores means a higher log rate) and back down after; move to Hyperscale, which has a higher and more consistent log rate; or split heavy transforms into a lakehouse/Spark step and load only the final result. Interview questions

Azure SQL Database vs Managed Instance: how do you choose?

MI when the application depends on instance-level features: Agent jobs, cross-database queries, CLR, Service Broker, linked servers, DB Mail, replication, or many databases that work together, and when you want the fewest code changes. SQL Database for new or modernized apps, SaaS with database-per-tenant (elastic pools), serverless needs, Hyperscale scale, and the least operational overhead. Both are PaaS with built-in HA, backups and patching.

Explain the Hyperscale architecture.

Compute and storage are separated into tiers. The primary compute node runs the engine with a large local SSD cache (RBPEX). Page servers each hold a range of data pages and keep them up to date by applying log. The log service receives log from the primary, hardens it in a landing zone and distributes it to page servers and replicas. Backups are snapshots of page server storage. So size limits reach 128 TB, backups are almost instant, restores are fast, and replicas can be added quickly because they share storage.

General Purpose vs Business Critical?

GP uses remote storage with the compute node failing over by restarting elsewhere: higher I/O latency (several ms), failover in tens of seconds, lower cost. BC uses local SSD with an AG of 4 replicas: I/O latency under a millisecond-ish, fast failover, a free read-only replica, and In-Memory OLTP support, at roughly double the price or more. Pick BC for latency-sensitive OLTP, GP for most others.

What are failover groups and how do apps use them?

A failover group contains one or more databases (SQL Database) or all user databases of an MI, replicated asynchronously to another region. It provides two DNS endpoints: read-write (always points to the current primary) and read-only (points to the secondary). Apps connect to the listener names, so after failover they don't change connection strings. Failover can be Microsoft-managed with a grace period, or customer-managed (recommended for most, so you decide on data loss).

What is Azure Hybrid Benefit?

A licensing benefit that lets you apply existing SQL Server core licences with Software Assurance (or subscriptions) to Azure SQL Database, MI and SQL VMs, paying only the base compute rate. Enterprise cores map to more vCores than Standard (1 Enterprise core covers 4 GP vCores or 1 BC vCore). It also provides 180 days of dual-use rights during migration. Combined with reserved capacity, savings can be large.

What's the SQL IaaS Agent extension?

An extension for SQL Server on Azure VMs that enables portal management features: licence model changes (pay-as-you-go vs AHB), automated backup and patching, storage configuration, Defender integration, and assessment best practices. Register every SQL VM with it.

How do you run scheduled jobs on Azure SQL Database?

There's no SQL Agent. Use elastic jobs (a job agent that runs T-SQL across many databases on a schedule), Azure Data Factory or Fabric pipelines, Azure Automation or Logic Apps, or Azure Functions with timers. For multi-tenant estates, elastic jobs are the closest to Agent.

How do you secure network access to Azure SQL?

Private endpoints into your VNet, with public network access disabled. If public access is needed, use server firewall rules limited to known IPs, and avoid "Allow Azure services" (it allows any Azure tenant's services). Use the redirect connection policy inside Azure for lower latency. Combine with Entra ID authentication, TLS 1.2+, and auditing of failed logins.

What resource governance errors might you see in Azure SQL, and what do they mean?

Error 10928/10936 (resource limit reached for workers or sessions), 40501 (service busy), 40613 (database not currently available, usually transient during reconfiguration), and waits like LOG_RATE_GOVERNOR or IO governance waits. They mean the tier is too small for the load or the app is opening too many concurrent requests. Fix by tuning queries, connection pooling, retry logic, or scaling up.

What is serverless in Azure SQL and when wouldn't you use it?

A compute tier that scales vCores automatically between a min and max and bills per second of use; in General Purpose it can auto-pause after an idle period (storage-only billing). Don't use it for steady, always-busy workloads (provisioned is cheaper), latency-sensitive apps that can't tolerate a resume delay of up to about a minute, or workloads that need features incompatible with auto-pause.

How do you move a database from Azure SQL back to on-prem?

From Azure SQL Database: export a BACPAC (slow for large databases), or replicate with transactional replication or a pipeline. From MI with the SQL Server 2022/2025 update policy: take a COPY_ONLY backup to URL and restore it to SQL Server 2022/2025, or use the MI link to fail back. With the always-up-to-date policy, native restore to on-prem isn't possible. Plan your exit path before you migrate.

Reports in Fabric slow down every day at 9 a.m., and users see throttling messages. What's going on?

The capacity is overloaded: the 9 a.m. report peak plus background jobs (refreshes, Spark notebooks, pipelines scheduled at the same time) exceed the capacity's CU. Fabric smooths background usage over 24 hours and interactive usage over a few minutes, but sustained overuse triggers interactive delays, then rejection. Open the Capacity Metrics app to find the top items by CU. Fixes: move heavy ETL off the peak, optimize the expensive items (Spark job sizing, Delta file compaction, DAX), separate ETL and BI onto different capacities, or scale up the F SKU (possibly only for peak hours).

Interview questions

What is OneLake and why does it matter?

A single, tenant-wide logical data lake that every Fabric item writes to, built on ADLS Gen2 and storing tables in open Delta Parquet. It removes copies between engines: Spark, the SQL endpoint, the Warehouse, KQL and Power BI all read the same data. Shortcuts virtualize external storage (ADLS, S3, GCS) without moving data. One copy means fewer pipelines, less drift and simpler governance.

What's a shortcut vs mirroring in Fabric?

A shortcut is a pointer to data that already lives in a lake format elsewhere (ADLS, S3, another OneLake item); no data is copied and queries read it in place. Mirroring continuously replicates an operational database (Azure SQL, SQL Server, Cosmos DB, Snowflake and others) into OneLake as Delta tables, so analytics run on Fabric compute without touching the source. Use shortcuts for files and lakes, mirroring for databases.

Explain Fabric capacity, smoothing and throttling.

A capacity provides a number of capacity units shared by all workloads in assigned workspaces. Operations consume CU-seconds. Fabric smooths consumption: interactive operations over minutes, background operations over 24 hours, so short bursts are allowed. If smoothed usage stays above 100%, Fabric first delays interactive requests, then rejects interactive and eventually background requests. Monitor with the Capacity Metrics app and size or split capacities accordingly.

What is Direct Lake?

A Power BI storage mode in Fabric. The semantic model loads columns directly from Delta Parquet files in OneLake into memory when needed (no scheduled import copy), giving import-like performance with data that's as fresh as the last Delta commit. Requirements: well-maintained Delta tables (V-Order, reasonable file and row-group sizes). It can fall back to DirectQuery through the SQL endpoint in some cases, depending on the Direct Lake flavor and features used.

What's the SQL analytics endpoint of a Lakehouse?

An automatically created read-only T-SQL endpoint over the Lakehouse's Delta tables. You can query with SQL Server tools, create views, functions and security, and connect Power BI, but you can't INSERT/UPDATE tables through it; writes go through Spark or pipelines. For full T-SQL DML use a Fabric Warehouse.

Serverless vs dedicated SQL pool in Synapse?

Dedicated: provisioned MPP compute with its own storage (distributions, CCI), predictable performance for heavy, constant warehouse workloads, billed per hour whether used or not (can pause). Serverless: no provisioning, queries files in the lake directly, billed per TB scanned; good for exploration, logical warehouses over Parquet and occasional queries. Serverless costs grow with scanned data, so partition and use Parquet.

What is V-Order?

A write-time optimization for Parquet in Fabric that applies special sorting, row-group distribution, dictionary encoding and compression. Files remain standard Parquet readable by any engine, but Fabric engines (especially Power BI Direct Lake and the SQL endpoint) read them faster. It costs some write time. It's enabled by default in many Fabric write paths.

How do you do CI/CD in Fabric?

Connect each development workspace to a Git branch (Azure DevOps or GitHub) so items (notebooks, pipelines, semantic models, reports, warehouses) are stored as code. Use feature branches and pull requests. Promote with Fabric deployment pipelines (dev, test, prod stages with deployment rules for connections and parameters) or with the Fabric REST APIs and fabric-cicd tooling in Azure DevOps/GitHub Actions. Warehouses can be managed with SQL database projects (DACPAC).

What are the main Fabric security layers?

Tenant settings (admin portal), capacity assignment, workspace roles, item permissions (share, read, build), OneLake data access roles and OneLake security for folders/tables/rows/columns, SQL-level security on the Warehouse and SQL endpoints (GRANT, RLS, CLS, DDM), semantic model RLS/OLS, sensitivity labels and DLP through Purview, plus network controls (private links, managed private endpoints, workspace identity).

Is Synapse being retired? How do you advise clients?

Synapse is still supported, but Microsoft's investment and new features go to Fabric, and Synapse dedicated pools don't get new capabilities. Advice: no new major builds on Synapse dedicated pools; plan migration to Fabric as part of the roadmap, starting with new workloads in Fabric, and move existing workloads when there's a business reason (cost, features, refresh of the platform), using Microsoft's migration tools.

Why might a SQL Server team prefer the Fabric Warehouse over the Lakehouse?

It's T-SQL from end to end: CREATE TABLE, INSERT/UPDATE/DELETE, stored procedures, multi-table transactions, familiar tools (SSMS, VS Code) and SQL database projects. The team reuses its skills while the data still lands as Delta in OneLake, open to Spark and Power BI. Spark-heavy or file-heavy work can still use a Lakehouse alongside.

Real-time scenarios

A Snowflake bill doubled in two months. How do you investigate and control it?

A Databricks pipeline writes thousands of tiny files per hour and queries on the table keep getting slower.

The small-files problem: each streaming micro-batch or high-partition write creates small Parquet files, so readers open thousands of files and the Delta log grows. Fixes: enable optimized writes and auto compaction, run OPTIMIZE regularly (or predictive optimization), reduce over-partitioning (partition only very large tables on low-cardinality columns, or switch to liquid clustering), increase trigger intervals for streams if latency allows, and VACUUM old files. The CIO asks: "Should we pick Fabric, Snowflake or Databricks?" How do you answer?

Interview questions

What are micro-partitions in Snowflake?

Snowflake automatically splits tables into immutable micro-partitions of about 50-500 MB uncompressed, stored in a columnar format. For each it keeps metadata such as min/max per column and distinct counts. Queries prune micro-partitions that can't match the filter. You don't manage them; for very large tables where natural load order doesn't match filters, you define a clustering key and automatic clustering re-organizes data (at a cost).

Time Travel vs Fail-safe?

Time Travel lets users query, clone or restore data as it was at a past point (AT/BEFORE, UNDROP), for 1 day by default and up to 90 days on Enterprise edition. Fail-safe is a further 7 days after Time Travel ends where only Snowflake support can recover data, for disasters; it's not user-accessible. Both add storage cost. Transient tables have no Fail-safe and at most 1 day of Time Travel.

Scale up vs scale out in Snowflake?

Scale up: a larger warehouse size (each size doubles compute and credits) makes complex individual queries faster. Scale out: a multi-cluster warehouse adds clusters of the same size when queries queue, handling more concurrent users; clusters are removed as load drops. Choose based on whether the problem is query complexity or concurrency.

What is zero-copy cloning?

Creating a copy of a database, schema or table that initially shares the same micro-partitions as the source, so it's instant and costs no extra storage. Only data changed after the clone takes new storage. Uses: dev/test environments from production, safe experiments, point-in-time copies combined with Time Travel.

What makes Delta Lake ACID?

The transaction log. Each commit writes a new numbered JSON file listing added and removed Parquet files; readers use the latest committed version, so they never see partial writes. Writers use optimistic concurrency: they check for conflicting commits before writing their entry and retry or fail on conflict. Checkpoint files summarize the log every so often for fast reads. Data files are never modified in place.

What is Unity Catalog?

Databricks' unified governance layer: one metastore per region attached to workspaces, a three-level namespace (catalog.schema.object), centralized ANSI-SQL style permissions, row filters and column masks, attribute-based policies, automatic lineage down to column level, audit logs, discovery, and governance of tables, views, volumes (files), functions and ML models. It replaces the per-workspace Hive metastore.

Liquid clustering vs partitioning vs Z-ORDER?

Partitioning physically separates files into folders by column values: great for very large tables with low-cardinality filters, bad when it creates many small partitions. Z-ORDER co-locates related values within files during OPTIMIZE, but must be re-run and works poorly with many columns. Liquid clustering (CLUSTER BY) incrementally clusters data on chosen keys, lets you change keys without rewriting the table, and avoids small-partition problems. It's the recommended default for new Delta tables.

What are Streams and Tasks in Snowflake?

A stream records change offsets on a table (inserts, updates, deletes since the stream was last consumed), exposed with metadata columns like METADATA$ACTION. Consuming the stream in a DML transaction advances its offset. A task runs SQL on a schedule or after another task (DAGs), optionally only when the stream has data. Together they implement incremental ELT. Dynamic tables are a declarative alternative: you define the query and a target lag, and Snowflake keeps it refreshed.

What is the medallion architecture?

A layering pattern for lakehouses. Bronze: raw data as ingested, append-only, with metadata. Silver: cleaned, de-duplicated, conformed and joined data with enforced schema. Gold: business-level aggregates and dimensional models for BI and ML features. Each layer is a set of Delta tables, and quality improves as data moves up. It's the lakehouse equivalent of landing, integration and presentation layers.

What are Lakeflow Declarative Pipelines (Delta Live Tables) expectations?

Data quality rules declared on pipeline tables, for example CONSTRAINT valid_gtin EXPECT (gtin RLIKE '^[0-9]{14}$') ON VIOLATION DROP ROW. Actions: keep and record the violation (warn), drop the row, or fail the update. Metrics are recorded in the pipeline event log, so you get data quality dashboards for free.

How does Snowflake handle concurrency differently from SQL Server?

Compute is isolated per virtual warehouse, so ETL and BI on different warehouses don't compete for CPU or memory, and reads never block writes (data is immutable micro-partitions with versioning). Concurrency within one warehouse is handled by queuing and multi-cluster scale-out. DML on the same table can still conflict (table-level locking for some operations), so concurrent heavy writers on one table should be serialized.

What is Delta Sharing / Snowflake Secure Data Sharing, and why would a CPG company care?

Both let you share live, read-only data with another organization without copying files or building extracts. Snowflake sharing works between Snowflake accounts (or reader accounts); Delta Sharing is an open protocol readable by Spark, pandas, Power BI and others. A CPG company can share sell-in and inventory data with retailers or receive POS data from them, and share data with agencies, without daily file transfers.

Lakehouse, medallion, Data Mesh and Data Fabric

A lakehouse keeps data in cheap open files in a lake but adds warehouse features (transactions, schemas, updates, time travel) through open table formats like Delta and Iceberg. Data Mesh is an organizational idea, not a product: each business domain owns and publishes its data as a product, on a shared self-service platform, under common governance rules. Data Fabric is a technology idea: a metadata-driven layer that connects and governs data wherever it lives.

Open table formats

  • Delta Lake (Databricks, Fabric): transaction log in _delta_log; MERGE, time travel, Change Data Feed, liquid clustering.
  • Apache Iceberg (Snowflake, AWS, Google, Dremio): metadata files, manifest lists and manifests; hidden partitioning and partition evolution; strong multi-engine support through REST catalogs (Polaris / Snowflake Open Catalog, Unity Catalog, Glue).
  • Apache Hudi: strong for upsert-heavy streaming ingestion.
  • Interoperability: Delta UniForm writes Iceberg metadata too; Fabric can read Iceberg through shortcuts; Apache XTable translates metadata. The format war is turning into "write once, read with anything".

Data Mesh: the four principles

  1. Domain ownership: the teams closest to the data (Sales, Supply Chain, Marketing, Finance) own their analytical data, not a central team.
  2. Data as a product: each data product has an owner, an SLA, documentation, quality metrics and versioned interfaces. Good data products are discoverable, addressable, trustworthy, self-describing, interoperable and secure.
  3. Self-serve data platform: a central platform team provides the tooling (storage, pipelines, catalog, CI/CD, monitoring) so domains don't each reinvent it.
  4. Federated computational governance: common standards (identifiers, security, quality, interoperability) agreed centrally and enforced automatically by the platform (policy as code), while domains keep autonomy.

Mapping to platforms: Fabric domains and workspaces with endorsement and the OneLake catalog; Databricks catalogs per domain in Unity Catalog with Delta Sharing; Snowflake databases per domain with shares and Horizon. A mesh fails when domains lack data skills, so most companies run a hybrid: central platform and core conformed data (product, customer, calendar), domain-owned products on top.

Other patterns you may be asked about

  • Data Fabric: active metadata, catalog, lineage, virtualization and automation that integrate data across sources. Complements a mesh (fabric is the "how", mesh the "who").
  • Lambda (batch + speed layer) vs Kappa (one streaming pipeline with replay).
  • Data contracts: agreed schemas, semantics, SLAs and quality rules between data producers and consumers, versioned and checked in CI.
  • Zero-ETL / mirroring: platform-managed replication from operational databases into analytics (Fabric mirroring, Snowflake and Databricks connectors).
  • Logical data warehouse / virtualization: query data in place through PolyBase, serverless SQL, shortcuts or Denodo, instead of copying.
  • Reverse ETL: pushing curated warehouse data back into operational tools (CRM, TPM).

Real-time scenarios

A CPG company's central BI team has a 9-month backlog. The Chief Data Officer wants to "do Data Mesh". What do you recommend?
  1. Treat it as an operating model change, not a tool purchase. Start with 2-3 domains that have data-savvy people and clear demand (for example Revenue Growth Management, Supply Chain).
  2. Build the self-serve platform first: workspace or catalog templates, pipelines, CI/CD, monitoring, a catalog, and security patterns that domains can use without tickets.
  3. Keep shared core data products central at first: Product, Customer/Retailer, Calendar, from MDM, so domains don't create competing versions.
  4. Define what a data product must have: owner, SLA, documentation, quality checks, access policy, version. Make the platform enforce what it can.
  5. Federated governance council with domain representatives; measure success by lead time and reuse, not by the number of products.
Data scientists want raw POS and IoT sensor data in Python; finance wants governed T-SQL star schemas. Do you need two platforms?

Not necessarily. A lakehouse serves both from one copy: raw and silver Delta tables for Spark/Python notebooks, and gold star schemas served through a SQL engine (Fabric Warehouse or SQL endpoint, Databricks SQL warehouse) for finance and Power BI. Governance (Unity Catalog or OneLake security plus Purview) applies to both. Keep separate compute so heavy data science doesn't slow finance queries.

Interview questions

Define a lakehouse in one or two sentences.

An architecture where data lives once in open file formats on low-cost object storage, and an open table format (Delta, Iceberg) adds ACID transactions, schemas, updates and time travel, so the same data supports BI, SQL, data engineering, streaming and ML from different engines.

What are the four principles of Data Mesh?

Domain-oriented ownership, data as a product, a self-serve data platform, and federated computational governance.

Data Mesh vs Data Fabric?

Mesh is socio-technical: it decentralizes ownership to domains and treats data as products. Fabric is technology-led: a metadata-driven integration and governance layer (catalog, lineage, virtualization, automation) that connects data across systems, usually run centrally. They can coexist: the fabric provides the platform capabilities a mesh needs. Note that "Microsoft Fabric" is a product name and supports both styles.

What makes something a "data product"?

A dataset (or API or model output) published by an owning team for others, with a clear owner, documented meaning and schema, an SLA on freshness and availability, quality checks with visible results, defined access and security, versioning so changes don't break consumers, and discoverability in a catalog. A table in a lake isn't a product until it has those properties.

Delta vs Iceberg?

Both add ACID transactions, schema evolution and time travel on Parquet. Delta uses an ordered log of JSON commits with checkpoints and is native to Databricks and Fabric. Iceberg uses a tree of metadata, manifest lists and manifests, supports hidden partitioning and partition evolution, and has broad engine support through REST catalogs (Snowflake, AWS, Trino). Interop features (Delta UniForm, Fabric shortcuts, XTable) increasingly let you read one as the other.

Why does the catalog matter so much in a lakehouse?

Files alone have no tables, permissions or lineage. The catalog (Unity Catalog, OneLake catalog, Polaris, Glue) maps table names to metadata locations, manages schemas and transactions, enforces access control, records lineage and makes data discoverable. Engine interoperability also depends on sharing a catalog. Without a governed catalog a lakehouse becomes a swamp again.

What is a data contract?

An explicit, versioned agreement between a data producer and its consumers: schema (fields, types, nullability), semantics (definitions), quality rules, SLAs (freshness, availability), and change policy. It's stored as code (YAML or JSON), validated in the producer's CI pipeline and at ingestion, so breaking changes are caught before they hit downstream reports.

Lambda vs Kappa architecture?

Lambda runs a batch layer (complete, accurate, slow) and a speed layer (real-time, approximate), merged in a serving layer: powerful but two code paths. Kappa uses only a streaming pipeline with a replayable log (Kafka, Event Hubs); reprocessing means replaying the log. Modern engines (Spark structured streaming, Delta, Fabric Eventstream) blur the line by letting one code path run as batch or stream.

What risks do you see with Data Mesh?

Domains without data engineering skills produce poor products; duplicated and inconsistent definitions (three "net sales"); higher total cost if every domain builds its own pipelines; governance gaps; and a weak platform that forces domains back to tickets. Mitigate with a strong platform team, shared core entities, automated governance and a gradual rollout.

Checklist of things that break

  • Instance-level dependencies: logins and SIDs, Agent jobs, linked servers, credentials, DB Mail profiles, server triggers, Service Broker routes, cross-database queries and three-part names, CLR assemblies, MSDTC.
  • Feature gaps: FILESTREAM/FileTable (not on MI or SQL DB), Windows authentication (move to Entra ID or Entra Kerberos), xp_cmdshell and file system access, trace flags.
  • Settings chosen at creation on MI: server collation and time zone. Get them right; they can't be changed later.
  • Applications: connection strings, hard-coded server names or IPs, firewall rules, driver versions and encryption settings, retry logic for transient errors.
  • BI stack: SSIS (Azure-SSIS IR or rebuild), SSRS (Power BI Report Server on a VM, or Power BI paginated reports), SSAS (Azure Analysis Services or Power BI semantic models).
  • Performance: compatibility level change, different storage latency and log rate limits in PaaS, network latency between app and database if they're not moved together.
  • Data transfer time: roughly 10 TB over 1 Gbps is about a day at full speed; plan online sync methods or Data Box.

Real-time scenarios

You lead migration of 300 SQL Server databases across 45 instances to Azure within 12 months. Describe your plan.
  1. Discover: Azure Migrate appliance or Azure Arc on all servers; collect at least 2-4 weeks of performance data including month-end.
  2. Assess: readiness per target (MI, SQL DB, VM), blockers, SKU and cost; map application dependencies (interviews plus connection data from sys.dm_exec_sessions and network flows).
  3. Decide per database: retire, retain, rehost, replatform or refactor; build a landing zone (networking, identity, policies, monitoring) first.
  4. Wave plan: pilot wave with low-risk apps; group databases by application and cross-database dependencies; schedule around business calendars (no cutovers at quarter-end close or peak promotions).
  5. Method per wave: MI link or LRS for MI, DMS online for VMs, backup/restore for small offline-tolerant ones.
  6. Rehearse: full test migration, performance test against baseline, timed cutover runbook, go/no-go criteria, rollback plan (keep the source read-only but intact until sign-off).
  7. Cutover and hypercare: monitor Query Store, waits and errors; tune; then right-size after 2-4 weeks of real data.
  8. Optimize cost: Azure Hybrid Benefit, reserved capacity, decommission source servers and licences.
Cutover weekend: the database is on MI, but the app is 3x slower than on-prem. What do you check?
  • Network latency between the app servers and MI (the app may still be on-prem, so every chatty call now crosses the WAN). Chatty apps need to move with the database.
  • Compat level and plan changes: compare Query Store at the source (if you had it) and now; force good plans.
  • Tier limits: General Purpose storage latency, IOPS per file (file size affects IOPS on GP), log rate; check waits (PAGEIOLATCH, WRITELOG, INSTANCE_LOG_RATE_GOVERNOR).
  • tempdb size and configuration on MI.
  • Stats: update statistics after migration.
  • Connection settings: redirect vs proxy connection policy, encryption overhead, connection pooling.
Migrating a 15-year-old Oracle warehouse (20 TB, PL/SQL-heavy ETL) to Fabric or Snowflake. What are the main workstreams?

Inventory (tables, PL/SQL packages, ETL jobs, reports, users) and usage analysis to drop unused objects; schema conversion with tooling plus manual fixes (data types, sequences, partitions); code translation of PL/SQL to T-SQL/Snowflake SQL or Spark, which is usually the biggest effort; historical data migration (export to Parquet, bulk load) and incremental sync during parallel run; ETL re-platforming; report re-pointing; data validation (row counts, checksums, business KPIs by period); performance testing; security model mapping; cutover per subject area; and decommissioning to stop Oracle licence costs.

Interview questions

Online vs offline migration?

Offline: stop the application, back up or export, copy and restore, then restart on the target. Downtime equals the whole transfer and restore time, so it works for small databases or flexible downtime windows. Online: the target is seeded and kept in sync continuously (MI link, LRS, DMS online, replication, distributed AG), and downtime is only the final cutover (minutes). Online needs more setup and monitoring but suits large or critical systems.

What is the Log Replay Service?

A Managed Instance feature that restores a database from full, differential and log backups you place in Azure Blob storage, continuously applying new log backups as they arrive. You cut over by taking a final tail-log backup on the source and telling LRS to complete. It works with any backup tooling and doesn't need network connectivity between source and MI (only to storage), unlike the MI link.

How do you validate a migration?

Data: row counts per table, checksums or hash aggregates on key columns, business KPIs (sales by month) matching the source. Schema: object counts, constraints, permissions. Function: application test scripts and user acceptance. Performance: top queries from the baseline compared using Query Store, batch job durations, peak-load test. Operations: backups, monitoring, alerts, DR failover on the target all tested before sign-off.

What's in a cutover runbook?

A timed step list with owners: pre-checks (sync healthy, backups complete), communication, application freeze, final sync (tail-log backup or link failover), validation queries, connection string or DNS switch, job enablement on the target, smoke tests, go/no-go decision point, rollback steps and their deadline, and post-cutover monitoring. It's rehearsed at least once with real timings.

What's your rollback plan in a migration?

Keep the source database intact (read-only after cutover) until sign-off. For online methods, reverse the sync if possible (MI link failback on SQL 2022+, or replication back), otherwise accept that changes made on the target after cutover must be replayed or exported back. Define the decision deadline: after a certain point, fixing forward is cheaper than rolling back. Test the rollback path in rehearsal.

Why do collation and time zone matter when creating a Managed Instance?

Both are instance-level settings fixed at creation. The server collation affects tempdb and system databases, so a mismatch with the database collation causes "Cannot resolve the collation conflict" errors in queries joining temp tables. Time zone affects GETDATE(), SYSDATETIME() and Agent job schedules; most MIs default to UTC, which can break apps that assume local time. Match the source instance or fix the code first.

How do you size the Azure target?

Collect real performance data over a representative period (CPU, memory, IOPS, throughput, log rate, storage) and use Azure Migrate SKU recommendations as a starting point, mapping to vCores with headroom. Check tier limits for log rate and IOPS, not just CPU. Consider that the target may be more efficient (newer engine) or less (higher storage latency on GP). Start a bit bigger, then right-size after a few weeks in production.

What is Azure Arc-enabled SQL Server and why would you use it in a hybrid estate?

An agent that projects on-prem or other-cloud SQL Servers into Azure as resources. Benefits: central inventory, best-practice assessments, Defender for SQL, Entra ID authentication and Purview for on-prem, pay-as-you-go licensing and ESU billing, migration assessments and MI link setup, and Fabric mirroring for SQL Server 2025. It's the management layer for the servers you "retain".

How long does it take to move 50 TB over the network?

At a sustained 1 Gbps (~110-120 MB/s real), roughly 5 days; at 10 Gbps, around half a day, if source storage and target ingestion keep up. Real throughput is often lower. So for big databases, seed early and keep in sync online (backups to Blob plus LRS or MI link), compress backups, or use Azure Data Box for the initial copy.

Security, governance and compliance

Database security is layers: control who can connect (authentication), what they can do (authorization), what they can see (encryption, masking, row-level security) and prove what happened (auditing, ledger). Governance adds the business side: classify data, assign owners, define policies and show regulators that the controls work.

Authentication

  • Prefer Windows/AD or Microsoft Entra ID (MFA, conditional access, groups) over SQL logins. In Azure use managed identities for apps and pipelines, so there are no passwords at all.
  • SQL logins only where unavoidable: password policy on, no shared accounts, rotate secrets via Key Vault; 2025 hashes passwords with PBKDF2.
  • Service accounts: group managed service accounts (gMSA), least privilege, correct SPNs for Kerberos (needed for double-hop and linked servers).
  • Contained database users for portability (and in AGs before contained AGs).

Authorization

  • Grant to roles, not users; map AD/Entra groups to roles.
  • Use schemas as security boundaries (GRANT SELECT ON SCHEMA::rpt).
  • Apps get EXECUTE on procedures (ownership chaining hides tables) or specific table rights. Never db_owner or sysadmin for apps.
  • Module signing or EXECUTE AS for procedures that need elevated rights (for example dynamic SQL or cross-database access) instead of granting the rights to users.
  • 2022+ built-in server roles (##MS_ServerStateReader## etc.) for monitoring and operations without sysadmin.
  • Regular access reviews; separation of duties (DBAs administer, auditors audit, security manages keys).

An audit finds that 40 developers have db_owner in production and the app connects as sa. Build the remediation plan.

Under GDPR a customer asks to be deleted. Their data is in OLTP, temporal history tables, the warehouse (SCD2), the lakehouse, and 35 days of backups.
  • Find all locations through classification and lineage (Purview) and a master key mapping for the person.
  • OLTP: delete or anonymize. For temporal tables, turn off system versioning briefly to purge history rows (or use the history retention policy), then turn it back on, under change control.
  • Warehouse and lake: anonymize the dimension rows (keep surrogate keys so facts still aggregate); for Delta tables, DELETE then VACUUM after the retention period so old files go away.
  • Backups: usually acceptable to let them age out within the documented retention, as long as a restore process re-applies deletions (keep a "deleted subjects" list applied after any restore).

The security team wants national ID and salary columns protected even from DBAs, while HR's app keeps working.

Use Always Encrypted. The column master key lives in Azure Key Vault (or the Windows certificate store on HR app servers), and the column encryption key is stored encrypted in the database. Only the HR app's driver can decrypt, so DBAs see ciphertext. Use deterministic encryption for national ID if the app looks it up by equality; randomized for salary. If the app needs range queries or sorting on encrypted data, use secure enclaves. Plan for: key rotation, no server-side computations on randomized columns without enclaves, reporting tools that need decrypted data (give them a separate, controlled path), and testing with the app's driver version.

Interview questions

TDE vs Always Encrypted: when do you use each?

TDE encrypts data files, log files and backups at rest, transparently, with no app change. It protects against stolen media but not against anyone who can query. Always Encrypted encrypts specific columns in the client driver; SQL Server never sees plaintext or keys, so it protects against DBAs, cloud operators and server compromise, but needs app and driver support and limits queries on those columns (unless using enclaves). Use TDE as baseline everywhere; Always Encrypted for the few most sensitive columns.

Deterministic vs randomized encryption in Always Encrypted?

Deterministic always produces the same ciphertext for the same value, so it supports equality lookups, joins, GROUP BY and indexing, but leaks patterns for low-cardinality data (for example gender). Randomized produces different ciphertext every time: more secure but no server-side operations without secure enclaves. Deterministic columns need a BIN2 collation for strings.

Is Dynamic Data Masking a security feature?

It's an exposure-reduction feature, not a security boundary. It masks values in query results for users without UNMASK, which helps for support screens and casual access. But a user who can run ad hoc queries can infer values (WHERE Salary > 100000) or copy data into a temp table in some cases. Combine with proper permissions, RLS or Always Encrypted for real protection.

How does Row-Level Security work, and what are its performance considerations?

An inline table-valued function (the predicate) is attached to tables through a security policy. Filter predicates silently remove rows on reads; block predicates prevent writes that violate the rule. The function is applied like a join to every query, so keep it simple and sargable, index the lookup table, avoid scalar functions, and use SESSION_CONTEXT for app-supplied identities (set once per connection). Test plans with and without the policy.

What happens if you lose the TDE certificate?

You can't restore or attach the database or its backups on any other server, ever. TDE certificates (with private keys) must be backed up and stored securely and separately from the backups, and tested by restoring a backup on another server. With customer-managed keys in Azure Key Vault, protect the vault with soft delete and purge protection.

Explain ownership chaining and why it matters for security.

When a procedure or view accesses objects owned by the same owner, SQL Server doesn't check the caller's permissions on those underlying objects. So you grant EXECUTE on a procedure (or SELECT on a view) and users never need table permissions. It breaks when the owners differ or with dynamic SQL, where the caller's permissions are checked; use module signing or EXECUTE AS then. Cross-database ownership chaining should stay off.

What should a SQL Server audit cover for SOX or PCI?

Successful and failed logins, changes to logins, users, roles and permissions, DDL changes (schema changes), changes to audit configuration itself, access to sensitive tables (SELECT/UPDATE/DELETE on financial or cardholder data), use of elevated accounts, and backup/restore operations. Send audit logs to a SIEM that DBAs can't alter, and review them regularly.

How do you prevent SQL injection?

Parameterized queries in applications (never concatenate user input), sp_executesql with parameters in dynamic SQL, QUOTENAME and whitelisting for dynamic object names, least-privilege app accounts so injected code can do little, stored procedures as the access layer, input validation, and monitoring (Defender for SQL detects injection patterns).

What is crypto-shredding?

Encrypting each data subject's personal data with its own key. To "erase" the person, destroy the key: all copies (including in backups, logs and lakes) become unreadable without having to find and rewrite them. It's a practical answer to GDPR erasure across immutable or historical stores, at the cost of key management complexity.

What does Microsoft Purview add for a data architect?

A map of the data estate across clouds and on-prem (scanning, automatic classification of sensitive data), a business glossary and catalog with owners and data products, end-to-end lineage, data quality rules and scoring, sensitivity labels and DLP that follow data into Fabric and Office files, and access governance. It's the evidence layer for audits and the discovery layer for analysts.

What is "least privilege" in concrete SQL Server terms?

Apps get only EXECUTE on their schemas or specific DML rights; no db_owner, no ddladmin in production. Reporting users get SELECT on reporting schemas or views. DBAs use separate admin accounts with just-in-time elevation. Monitoring tools get server state roles, not sysadmin. Service accounts aren't local admins. Every grant goes to a role mapped from a group, and is reviewed periodically.

How do you manage secrets for pipelines and apps?

Prefer managed identities so there's no secret at all. Otherwise store secrets in Azure Key Vault, referenced by ADF/Fabric linked services, app configuration and SQL credentials, with RBAC on the vault, rotation policies, and logging of secret access. Never put passwords in SSIS packages, code repositories or connection strings in plain config files.

MDM concepts

  • Master vs reference vs transactional: master data are core entities (product, customer); reference data are code lists (country, currency, UOM); transactional data are events (orders, shipments).
  • Implementation styles:
    • Registry: keeps only cross-references and match results; sources stay as they are. Light, fast to start, read-only.
    • Consolidation: copies and merges source data into a golden record for analytics; sources unchanged.
    • Coexistence: golden record is built centrally and synced back to sources; both can change.
    • Centralized (transactional): records are created and maintained in the MDM hub only, then distributed. Strongest control, most change management.
  • Match and merge: deterministic rules (same GTIN) and probabilistic/fuzzy rules (similar name + address), with thresholds for auto-merge vs steward review.
  • Survivorship: which value wins in the golden record: most trusted source per attribute, most recent, most complete, or steward decision.
  • Cross-reference (xref): maps every source key to the master ID, which the warehouse uses to conform dimensions.
  • Stewardship: business owners and stewards with workflows for new records, merges, and exceptions; hierarchy management (category trees, retailer banners).
  • CPG specifics: GS1 identifiers (GTIN for products, GLN for locations), GDSN for syndicating product data to retailers, PIM for marketing content alongside MDM, SAP customer hierarchies (sold-to, ship-to, bill-to, payer).
  • Tools: Profisee (Azure-native, Purview integration), Informatica MDM, Reltio, Stibo STEP, Semarchy, SAP MDG. Microsoft MDS is removed in SQL Server 2025.

Interview questions

What's the difference between data quality and data governance?

Governance is the framework of decision rights, policies, roles (owners, stewards), standards and processes for managing data. Data quality is one outcome governance manages: measuring and improving whether data is fit for use. Governance decides who defines "active customer" and what quality threshold is acceptable; data quality checks enforce and report it.

Explain the four MDM implementation styles.

Registry: the hub stores only match links and cross-references; least invasive, no golden attributes stored. Consolidation: the hub builds golden records from source copies for downstream analytics; sources aren't updated. Coexistence: golden records are maintained centrally and synchronized back to sources, which can also still edit. Centralized: all creation and changes happen in the hub, which distributes records; highest control and highest organizational change.

What are survivorship rules?

Rules that decide which source value becomes the golden record value when matched records disagree, usually per attribute: source priority (trust ranking), most recent update, most complete or longest value, most frequent value, or manual steward choice. They must be documented and agreed with data owners because they directly change what reports show.

How do you measure data quality and report it?

Define rules per critical data element tied to a dimension (completeness, validity, uniqueness...), run them on each load or on a schedule, store results (rule, dataset, run time, passed and failed counts) in a DQ results table, and show scores and trends per domain, source and owner in a dashboard. Set thresholds that trigger alerts or block publishing. Track issues to resolution at the source.

Where should data quality checks run: source, pipeline or report?

As early as possible: at entry in the source or MDM (prevents bad data), then in the pipeline on ingestion and before publishing to gold (detects and quarantines), then monitoring in reporting (reconciliation and anomaly detection). Fixing only in the warehouse hides the problem and creates mismatches with source systems, so feed issues back to the source owners.

What's the replacement plan if a company uses SQL Server MDS today?

MDS is removed in SQL Server 2025 but still supported on 2022 until its end of support. Options: keep MDS on SQL 2022 short term; move to a commercial MDM (Profisee is the closest Microsoft-aligned option, with an MDS migration path); or for simple reference-data cases, build governed tables with a Power Apps stewardship UI and approval flow. Export models, entities, business rules and hierarchies, and plan the integration changes (subscription views used by ETL).

Deterministic vs probabilistic matching?

Deterministic matching uses exact rules (same GTIN, same tax ID, same normalized email). It's precise and explainable but misses variants. Probabilistic (fuzzy) matching scores similarity across several attributes (name with Jaro-Winkler or edit distance, address, phone) with weights, and auto-merges above a high threshold, sends a middle band to stewards, and rejects below. SQL 2025 adds EDIT_DISTANCE and JARO_WINKLER functions that help build this in T-SQL.

What is reference data management and why separate it from MDM?

Reference data are controlled code lists (countries, currencies, units of measure, channel codes, promotion types) and their mappings between systems. They change rarely, are small, and need versioning and approval, but not matching and merging. Managing them separately (a simple governed service or tables with workflow) avoids overloading the MDM tool and gives consistent codes to all pipelines.

Data platforms for AI, machine learning and vector search

Machine learning learns patterns from historical data, so it needs lots of clean, consistent history, with the right features (input columns) as they were known at each point in time. Generative AI apps (chatbots, copilots) mostly need retrieval: finding the right documents or rows to give the model as context, using vector search. The data architect's job is to supply both reliably and securely: quality, lineage, freshness, access control, and cost control.

What AI and ML need from the platform

  • History and point-in-time correctness: training data must use only what was known at prediction time (no "future leakage"). SCD2 dimensions, snapshot facts and Delta time travel make this possible.
  • Reproducibility: version datasets (Delta versions, snapshot tables) and record which version trained which model (MLflow).
  • Feature store: shared, documented features with an offline store (for training) and an online store (low-latency serving), so training and serving compute features the same way.
  • Unstructured data: documents, images and transcripts in the lake, with metadata and access control.
  • Governance: lineage of training data, PII handling (masking, consent), access trimming at retrieval time, audit of prompts and outputs, responsible AI reviews.
  • Serving: predictions written back to tables or APIs for apps and reports; monitoring of drift.

RAG architecture

  1. Ingest documents and records; extract text; split into chunks (by size with overlap, or by structure such as headings).
  2. Embed each chunk with an embedding model and store vector + text + metadata (source, owner, security tags, version).
  3. Retrieve: embed the user's question, run vector search (often hybrid with keyword search), filter by metadata and the user's permissions, optionally rerank.
  4. Generate: pass the top chunks and the question to an LLM with instructions to answer from the context and cite sources.
  5. Evaluate and monitor: groundedness, relevance, latency, cost; feedback loop.

Fabric data agents, Power BI Copilot and similar tools work best this way.

Interview questions

What is RAG and why is it used instead of fine-tuning?

Retrieval-augmented generation retrieves relevant, current content from your data at question time and gives it to the LLM as context. It keeps answers grounded in your data, supports citations, reflects updates immediately (no retraining), and respects access control at retrieval. Fine-tuning changes the model's behavior or style but is expensive, gets stale, and doesn't enforce permissions. Most enterprise assistants use RAG, sometimes with fine-tuning for format.

How do you choose chunk size for RAG?

Small chunks (100-300 tokens) give precise matches but lose context; large chunks (800-1,500) keep context but dilute relevance and cost more tokens. Common starting point: about 300-800 tokens with 10-20% overlap, or structure-aware chunking by headings and sections. Include titles and metadata in the chunk. Test retrieval quality with real questions and adjust.

What is training-serving skew and how does a feature store help?

The model sees features computed one way during training (batch SQL over history) and another way in production (app code in real time), so predictions degrade. A feature store defines each feature once, materializes it to an offline store for training (with point-in-time joins) and an online store for serving, so both use the same logic and values.

What is data leakage in ML, and how does data modeling prevent it?

Using information in training that wouldn't have been available at prediction time (for example final promotion results when forecasting before the promotion). It produces models that look great in testing and fail in production. Prevent it with point-in-time joins (as-of the prediction date), SCD2 history and snapshot tables, event timestamps on every feature, and time-based train/test splits.

Hybrid search: what is it and why use it?

Combining vector (semantic) search with keyword (lexical, BM25/full-text) search and merging results (for example reciprocal rank fusion), often with a reranker. Vectors find meaning ("snacks without gluten"), keywords find exact terms (SKU codes, product names, error numbers) that embeddings handle poorly. Hybrid usually beats either alone for enterprise content.

What governance controls do you put around AI use of enterprise data?

Data classification and exclusion of restricted data from indexes, security trimming at retrieval, PII masking in prompts and logs, approved models and endpoints (private networking, no training on your data), logging of prompts, retrieved sources and responses, evaluation for accuracy and harmful output, cost quotas, lineage from source to index, and an owner for each AI data product.

How would you store and track forecast versions in the warehouse?

A periodic snapshot fact keyed by forecast version (date generated, model version, scenario), target period, product and customer, with forecast quantity and optionally prediction intervals. Never overwrite: each run is a new version. Join to actuals by target period to compute accuracy by lag (1-week-ahead, 4-weeks-ahead). Partition by forecast date and use columnstore because it grows quickly.

What is MLOps, and where does the data architect fit?

MLOps applies DevOps practices to ML: versioned data and code, automated training pipelines, model registry and approval, automated deployment, and monitoring of performance and drift with retraining triggers. The data architect provides reliable, versioned, governed data pipelines and feature tables, lineage, the storage for predictions and monitoring data, and the integration of model outputs back into business systems.

Interview questions

Why shouldn't stored procedures use the sp_ prefix?

SQL Server treats sp_ as system procedures: it first looks for the procedure in master, then in the current database, which adds overhead and can cause cache misses. If Microsoft later adds a system procedure with the same name, yours may be hidden. Use schema plus a descriptive verb-noun name instead.

State-based vs migration-based database deployments?

State-based: you maintain the desired end-state schema (SQL project), and a tool (sqlpackage) generates the diff script against each target. Easy to see the full schema, good for drift detection, but complex data migrations (renames, splits) need pre/post-deployment scripts and refactor logs. Migration-based: you write ordered change scripts; precise control over data changes and order, simple to apply, but the current schema is spread across scripts. Many teams use state-based for schema plus scripted data migrations.

How do you make schema changes with zero downtime?

Use backward-compatible steps (expand and contract): add new nullable columns or new tables, deploy code that handles both old and new, backfill data in batches, switch reads to the new structure, then drop old structures in a later release. Use online index operations with WAIT_AT_LOW_PRIORITY, avoid size-of-data operations during business hours, and use short lock timeouts with retries in deployment scripts.

How do you unit test database code?

With tSQLt (tests written in T-SQL): fake tables (tSQLt.FakeTable) to isolate data, spy procedures, assert results (AssertEqualsTable), and run in transactions that roll back. Run tests in CI on every pull request against a disposable database (for example in a container). Add data quality and integration tests for pipelines (dbt tests or SQL assertions).

What's an architecture decision record?

A short document capturing one significant decision: context, options considered, the decision, and its consequences (trade-offs, risks). Stored in the repository next to the code, numbered and immutable (superseded by new ADRs, not edited). It explains to future teams why the design is the way it is, which is very useful in reviews and audits.

How do you run a design review for another team's database?

Ask for the requirements and non-functional requirements first, then review against a checklist: model and grain, keys and data types, indexes against the main query patterns, security model, HA/DR and backup, monitoring, growth and capacity, cost and licensing, compliance. Give prioritized findings (must fix before go-live, should fix, nice to have) with reasons and options, not just rules. Follow up on the must-fix items.

What belongs in a database runbook?

System overview and contacts, architecture diagram, dependencies, start/stop and failover procedures, backup and restore steps with locations, common alerts and their response steps, known issues and fixes, maintenance jobs and schedules, escalation path, and DR procedure with expected timings. Keep it versioned and test it in drills.

How do you mentor DBAs and developers on performance as a technical lead?

Shared standards and a code review checklist; reviewing real plans together; a regular "query clinic" using Query Store top offenders; documented patterns (upserts, pagination, batching, dynamic search); giving developers safe access to Query Store and plans in lower environments; and pairing on incidents so knowledge spreads beyond the senior DBA.

Definitions and quick differences

DELETE vs TRUNCATE?

DELETE logs each row, fires triggers, can have a WHERE clause, keeps identity values. TRUNCATE deallocates pages (logged minimally, still transactional and can be rolled back), resets identity, needs ALTER permission, doesn't fire DELETE triggers, and fails if the table is referenced by a foreign key.

UNION vs UNION ALL?

UNION removes duplicates (adds a sort or hash); UNION ALL keeps all rows and is faster. Use UNION ALL unless duplicates must be removed.

ROW_NUMBER vs RANK vs DENSE_RANK?

ROW_NUMBER: unique 1,2,3,4. RANK: ties share a rank and leave gaps (1,1,3). DENSE_RANK: ties share a rank without gaps (1,1,2).

SCOPE_IDENTITY vs @@IDENTITY vs IDENT_CURRENT?

SCOPE_IDENTITY: last identity in the current session and scope (use this, or OUTPUT). @@IDENTITY: current session, any scope, so a trigger insert can change it. IDENT_CURRENT('table'): last identity for that table from any session.

What does SET XACT_ABORT ON do?

Makes most run-time errors abort and roll back the whole transaction, instead of only the failing statement. Recommended in procedures with explicit transactions, and required for some distributed transactions.

What's a covering index?

An index that contains every column a query needs (in key or INCLUDE), so no lookup to the base table is required.

What's a trusted foreign key?

One that SQL Server has verified for all existing rows (is_not_trusted = 0). Constraints re-enabled without WITH CHECK stay untrusted, and the optimizer can't use them for join elimination.

What is an orphaned user?

A database user whose SID doesn't match any login on the instance, typically after a restore or failover to another server. Fix with ALTER USER ... WITH LOGIN = ..., and prevent by creating logins with the same SID.

What is a database snapshot?

A read-only, point-in-time view of a database using sparse files and copy-on-write of changed pages. Used for reporting at a point in time or quick revert before risky changes. It's not a backup: it depends on the source database files.

What does READPAST do?

Skips rows locked by other transactions instead of waiting. Used with UPDLOCK and ROWLOCK for queue processing so workers don't block each other.

What does DBCC CHECKDB WITH PHYSICAL_ONLY check?

Page structure, checksums and allocation consistency, skipping the logical checks. Much faster, used for frequent checks on very large databases, with a full CHECKDB less often (or on a restored copy).

Does instant file initialization apply to log files?

Traditionally no, only data files (log must be zeroed). From SQL Server 2022, log growths up to 64 MB can benefit from IFI.

What is MIN_ACTIVE_ROWVERSION?

The lowest rowversion value still in use by an active transaction in the database. Using it as the upper bound of an incremental extract prevents skipping rows from transactions that commit late.

What is ApplicationIntent=ReadOnly?

A connection string option that tells the AG listener (or Azure SQL Business Critical/Hyperscale) to route the connection to a readable secondary through read-only routing.

What is a SARG?

A search argument: a predicate written so an index can be used to seek (bare column compared with a value or range).

What's the Unity Catalog namespace?

Three levels: catalog.schema.object.

What folder holds the Delta transaction log?

_delta_log in the table's root, with JSON commit files and Parquet checkpoints.

What are Snowflake's three architecture layers?

Storage, compute (virtual warehouses) and cloud services.

What's a OneLake shortcut?

A pointer that makes data in another location (ADLS, S3, GCS, another OneLake item) appear in a Lakehouse without copying it.

RPO vs RTO, in one sentence each?

RPO: how much data (in time) you can afford to lose. RTO: how long you can afford to be down.

What is a conformed dimension?

A dimension with the same keys, attributes and meaning across all fact tables and marts, enabling drill-across analysis.

What is a factless fact table?

A fact table with keys but no numeric measures, recording events or coverage, such as which products were on promotion in which stores.

What does SCD type 2 need in the table?

A surrogate key, the durable business key, effective-from and effective-to dates, and usually a current-row flag (plus a hash for change detection).

What does CDC need on-prem that Change Tracking doesn't?

SQL Server Agent jobs (capture and cleanup). Change Tracking works synchronously within transactions and needs no Agent.

Recommended starting number of tempdb data files?

One per logical core up to 8, all equal size; add in groups of 4 only if allocation contention remains.

What are the Data Mesh principles, in four words?

Domain ownership, data-as-product, self-serve platform, federated governance.
